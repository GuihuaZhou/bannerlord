## 一、不可更改的最终 UI 要求

1. **整体外形**：完整、平整的长方形窗口；「封建兵管理」标题直接镶嵌在矩形内部，不设置向上突出的独立标题框。
2. **删除在籍总数统计行**：不要另设「在籍总数」整行；窗口顶部仅保留「待役 / 在役 / 返乡冷却」三个状态及人数，下面采用相应状态标签切换。来源列表中可以继续显示各村庄总兵数以便辨识。
3. **左侧来源范围**：城镇/城堡可选择「全部附属村庄」或某个直属村庄；村庄入口只能查看和操作本村封建兵，不允许切换其他村庄。
4. **中间兵员列表**：优先使用现有原版士兵卡片/选择器资源，保留兵种图像、人数、可选择的加号等原生交互；切换待役、在役和冷却状态时展示对应兵员。
5. **删除右侧兵种信息区**：不增加右侧信息栏，也不增加独立数量步进器或征召/解散快捷按钮。
6. **底部**：士兵卡片列表下方只显示「选择的人员（已选 / 可选）」；最底部仅使用原版「取消」和「完成」两个按钮。
7. **不改变美术风格**：沿用截图展示的原版石纹边框、深色底、卡片、中文字体和按钮，不引入新的整套配色、现代化仪表盘或复杂图标体系。

## 二、显示范围与状态

| 入口 | 默认数据范围 | 允许切换来源 | 待役 | 在役 | 返乡冷却 |
|---|---|---|---|---|---|
| 城镇 | 当前城镇附属全部村庄 | 是 | 显示汇总与明细 | 显示汇总与明细 | 显示汇总与明细 |
| 城堡 | 当前城堡附属全部村庄 | 是 | 显示汇总与明细 | 显示汇总与明细 | 显示汇总与明细 |
| 村庄 | 当前村庄 | 否 | 只显示本村 | 只显示本村 | 只显示本村 |

统计口径：
- **待役**：按 `VillageFiefData.GetReadyRoster()` 中属于当前封邑模板的兵种统计；完整展示待役（含伤员），但征召仅开放满足现有征召审批的可用兵员。
- **在役**：按 `VillageFiefData.ServiceBatches` 中来源村庄统计；既包括玩家当前队伍也包括其他领主部队，展示总量；仅当前玩家部队中、符合来源范围且由现有事务认可的在役兵可解散。
- **返乡冷却**：按 `VillageFiefData.ReturnBatches` 统计，仅查看、不可操作。
- **兵种重叠**：同一 `CharacterObject` 来自不同村庄时，展示层可以汇总，但操作必须保留村庄来源映射，不得把其他村庄兵员混入本村操作，也不得把原生民兵/普通士兵当封建兵。
- UI 数字随来源筛选、状态切换和操作完成刷新。无兵可选时正确显示 `0 / 0` 并禁用完成提交。

## 三、交互流程

### 1. 待役：征召
- 点击「待役」标签，在卡片上使用原版加减号选择各兵种与人数。
- 点击「完成」执行征召；优先复用现有 `FiefPartyManager.ManualRecruitFromFief`、`RecruitFiefTroopsFromSettlement`、`FiefPartyData.RecruitManualSelection` 及内部统一事务。
- 仅允许健康且可征召的待役兵通过；遵守队伍容量、Hearth 动员消耗、村庄恢复锁定、封邑所有权及操作地点等既有规则。
- 从城镇/城堡可在全部附属村庄范围征召，或限定某一村庄；村庄只能征召本村。

### 2. 在役：解散
- 点击「在役」标签，展示所有符合来源筛选的在役兵员。
- 其他部队在役封建兵只读；可选择部分只能来自当前玩家队伍中的有效服役批次。
- 原版卡片加减号选择需解散的数量，点击「完成」后按源村和批次调用既有返乡事务。
- 复用 `FiefPartyManager.TryReturnFiefTroops` / `FiefReturnService.TryReturn` / `FiefPartyData.TryCommitFiefReturn`，如现有 API 不方便按兵种/部分数量定向返乡，可新增**最薄的安全服务入口**，不要直接修改 `TroopRoster`、`ServiceBatches`、`ReturnBatches`、`MobilizedHearth`。
- 返回后进入原有冷却流程，正确更新服役批次及村庄 Hearth；不得跨村解散。

### 3. 返乡冷却：只读
- 可以按兵种查看人数，不可选择，不允许提交任何数量。
- `完成` 在此页仅作为关闭/返回行为时应明确处理，不可触发征召或解散。

### 4. 窗口退出
- `取消` 不修改游戏数据。
- `完成` 只提交当前标签、当前来源范围和当前选择的**一种明确操作**（待役=征召，在役=解散，冷却=只读）；不能混合提交两个方向。
- 操作失败或部分成功时展示现有游戏反馈，刷新后以真实结果为准。

## 五、实现边界及风险

1. **不要重写既有业务模型**，不调整兵源日生产、Hearth 供养/动员、职业兵生产、税赋减免、身份转换、军饷规则。
2. 在役与返乡冷却不是普通 `GetFiefTroopRoster()` 内容，不要直接把它们写回村庄待役Roster来达到显示效果。展示使用独立只读快照或临时聚合Roster。
3. 兵种卡片展示共享 `CharacterObject` 不代表身份可凭兵种唯一识别；提交必须保留准确的来源与批次约束。
4. 切换村庄/标签后清空旧选择，防止筛选变更后提交过期人数。预览/提交之间发生名册变化时重新验证。
5. 编译/运行时以用户本地游戏和依赖 DLL 的真实签名为准。若原版 `OpenTroopSelection` 不支持「来源列表+三个标签」组合，不应强行臆造接口；可采用现有 `GameMenu` 来源/状态筛选加原生选择弹窗的**可实现降级方案**，明确报告视觉差异，再等待用户认可进一步改动。
6. 不覆盖本地未提交改动；如需新存档结构，必须注册正确的 Saveable 类型/容器并给出存档兼容验证结果。
