### 按顺序实施

1. 先绘制每种提交状态在执行器→业务 Service→Behavior→保存状态的闭环表。保留现有五态，不做全量重写。
2. `PartiallyCommitted`：原操作完成且不可重放；记录真实增加/减少的数量和批次，下一轮基于新权威状态批准**新尝试 ID**，而不是重新执行旧 Plan。
3. `RecoveryRequired`：建立冻结状态，不能像当前直接取消任务并当作普通补员重试；输出错误原因和可读、可恢复的源/目标指纹或快照。恢复只能先对账，未经证据不可补造资源。
4. 为已提交事务设计能在游戏 SaveSystem 中实际保存的最小记录，**先查可序列化类型和原有存档惯例**；不修改旧 SyncData 键、不重排 SaveIds。
5. 将 `ExecuteMercenary` 的 `operationId` 贯通购买事务防重；金币、市场、部队和预算四项部分失败能识别和阻断重复扣费。保留佣兵招募价格/概率。
6. 对 roster 回滚保留旧 `Action` 反向补偿机制，补齐对健康/伤员和目标实际数的回滚校验；不返回误导性的“精确已转人数”。
7. 测试完整/部分/零、陈旧快照、权限拒绝、源端扣除后异常、目标端加兵后异常、回滚失败、存档后同 ID 重入。
