# ModifiedArmy 日志揭示的逻辑问题：证据、根因与修复边界

## A. P0 已证实：驻军 `ActualClan` 为 null，导致双向合法调兵失败

### 真实日志证据（上传的 `ModifiedArmy.log` 行号）

| 原始行号 | 行动 | 身份信息 | 硬失败 |
|---|---|---|---|
| 88 | 泰伊斯在胡比亚，FieldToGarrison，送回13人 | sourceClan=clan_aserai_3；destinationClan=null；ownerClan=clan_aserai_3；kindsMatch=True；atSettlement=True | DestinationClanNull |
| 485 | 浮士托在俄尼拉，GarrisonToField，提取50人 | sourceClan=null；destinationClan=clan_empire_west_4；ownerClan相同；kindsMatch=True；atSettlement=True | SourceClanNull |
| 525 | 伊勒塔斯在胡比亚，GarrisonToField，提取63人 | sourceClan=null；destinationClan=clan_aserai_3；ownerClan相同；kindsMatch=True；atSettlement=True | SourceClanNull |
| 595 | 特弥翁在希巴勒·祖姆尔堡，GarrisonToField，提取117人 | sourceClan=null；destinationClan=clan_empire_south_2；ownerClan相同；kindsMatch=True；atSettlement=True | SourceClanNull |

日志另外出现19条 `Notice [统一调兵]` 失败，旧版显示相同模糊说明。上述**四个被新诊断覆盖的操作**均可确认为此归属条件阻断；不能未经证实宣称全部19次均由相同根因造成。

### 代码原因（main 基线）

- `ForceManagement/Models/PartyExchangeModel.cs` 中 `BuildRosterPlan` 先检查类型/位置/`IsAuthorizedRosterPair`，失败立刻返回 `InvalidOrUnsafeTransfer`。此时尚未进入兵种、财政或名册审批。
- `IsAuthorizedRosterPair` 比较 `source.ActualClan == destination.ActualClan == settlement.OwnerClan`。对于任一方向，如果真实驻军 `ActualClan` 未赋值，普通业务失败。
- `ForceManagement/Services/PartyExchangeService.cs` 的二次校验有一份独立的 `IsAuthorizedRosterPair`，必须同步改，否则规划批准、执行阶段依旧被拒绝。
- 原版 `code/GarrisonPartyComponent.cs` 以 `Settlement.OwnerClan.Leader` 表达真实驻军拥有者；`code/MobileParty.cs` 的 `ActualClan` 则是独立存储的字段。不能假设二者始终同步。

### 修复方案（要求独立 P0 Commit）

1. 新建纯查询方法，例如 `PartyOwnershipPolicy.TryGetEffectiveTransferClan(MobileParty party, Settlement settlement, out Clan clan)`：
   - `party == settlement?.Town?.GarrisonParty && party.IsGarrison` 时，必须先检验是该定居点唯一真实驻军，再从 `settlement.OwnerClan` 取得归属。
   - 对野战队伍仍只认可 `party.ActualClan`，**不能**从 `CurrentSettlement.OwnerClan` 借用身份。
   - 若驻军身份不真实、Settlement.OwnerClan为null，返回失败，不能当作免检。
2. `PartyExchangeModel.IsAuthorizedRosterPair` 和 `PartyExchangeService` 的所有双向、执行时校验调用**同一个只读策略**；避免前后不一致。
3. 对普通调动坚持“来源有效 Clan 与目标有效 Clan 与定居点 OwnerClan 一致”，且仍检查真实驻军对象、抵达、活动状态、战斗、围城、安全可调人数及容量。
4. `NewlyCapturedSettlement` 例外仍只适用原有允许方向，即同 Kingdom 的**真实新占领驻军接收士兵**；不扩大到随意跨Clan驻军提兵。
5. 绝不通过 `garrison.ActualClan = settlement.OwnerClan` 批量写数据修复；任何读档/变更领主的同步策略须另行立项评估。
6. 增加 C# 自动测试及实机测试：null ActualClan 的真实驻军、正常驻军、假冒驻军、不同 Clan、刚占领封邑、正在围城、驻留与战斗状态变化。验证调兵守恒、封邑服务台账、预留征粮队名额均未改变。

### 建议新日志

`[统一调兵] 胡比亚的驻军所属家族信息没有同步到部队数据，伊勒塔斯原计划领取63名士兵，本次没有调兵。` —— 仅在缺失确实**造成错误阻断**的旧版本输出 Warn（限制每天一次）；修复后发生时 Debug 记录原字段缺失但正常使用真实驻军归属，不应误报已失败。

## B. P0 已证实：中文语言覆盖模板占位符错误

- `ModifiedArmy/ModifiedArmy/ModuleData/Languages/CNs/modifiedarmy-zho-CN.xml` 的 `ModifiedArmy_ManpowerConsume/ProduceNoSupply/Produce/RecruitmentBlocked/Recruitment` 五组译文错误使用 `SETTLEMENT_ID` 而 C# `SetTextVariable("SETTLEMENT_NAME", settlement.Name)`。日志因此呈现“定居点=”空白。
- `ModifiedArmy_ManpowerConsume` 的 `TROOP_ID` 也不对应代码设置的 `TROOP_NAME`。在给定日志中有5次“兵种=”空白。
- `ModifiedArmy_ManpowerProduce` 的汉化版本丢掉 `MANIFEST`，使原本已经提供的兵种清单失去展示途径。
- `ModifiedArmy_TransportEvent` 的中文版省略了 `STATE`、`EVENT_AMOUNT`；目前的日志未能证明其导致运行时故障，但需按照真实模板语义校验信息完整性。

**修复仅改字符串模板并添加自动占位符一致性检查即可，不应改变生成、招募、俘虏或扣款逻辑。** 以基础XML中`{=本地化Key}`关联CN文件同名id，再检查 `{VARNAME}` 的集合，允许“有意隐藏的可选字段”仅在书面白名单中记录并附原因。

## C. P1 已证实：日志等级与实现注释不一致

源码 `Recruitment/Behaviors/GarrisonRecruitFromPrisonersBehavior.cs` 的 `LogProfessionalRecruitment` 注释说“Keep successful and failed recruitment at Info”，但调用的是 `ModLogger.FileNotice`。同时函数对 `recruitedCount <= 0` 直接提前返回，不会按注释记录失败（失败详情另有 Debug 消息）。

改为成功 `ModLogger.FileInfo`，失败留在聚合 Debug/限制重试告警；更新注释说明现有事实。无须为了日志而制造额外招募审批。

## D. P1 已证实：信息量失衡与重复事件风暴

- 612条中调试占455条，`AutoUpgrade` 168条、`FiefSettlementData` 144条，绝大多数重复定居点计算。
- 多条定居点符合守军最低要求且“外援申请0人”的状态被写为 Notice；这只是**正常无需向外增援**，不代表野战部队可以从驻军抽多少兵，两个方向的条件不相同。
- `统一调兵` 多次打印同一 Party 同一地点相同人数的错误通知，缺乏失败冷却和可读原因。
- 正常“职业兵补充2或4人”仍被写为 Notice。

建议：静态编制只在变化时出日志；AI 部队和驻军的日常“尚无行动”状态 Debug 或汇总 Info；同一 Party 的同一失败按游戏日限制 Notice/Warn 次数，Debug 保留操作ID和可查证事实；正常入伍和消费 Info 不弹界面。

**注意**：限频只限“日志”，不要借这个需求顺手改变调兵路径和冷却时间；“失败后是否需要任务冷却”需依据修复后的实际情况再另行定业务方案。

## E. P2 值得调查：驻军职业兵存在“训练候选却批准0人”

真实记录：

- 胡比亚两天均有4名候选，每日上限为0，批准0，原驻军410人（行102—104、533—535）。
- 费卡翁有4名候选、每日上限4、批准0，驻军358人（行110—112、538—540）。
- 萨赫勒堡有2名候选、每日上限4、批准0，驻军304人（行478—480、590—592）。
- 俄尼拉曾有4名候选、批准4、实际4，次日4名候选只批准2且实际招募2（行115—120、543—547）。

**不能据此认定有兵可补却错误拒绝**。`GarrisonRecruitmentCapacity` 同时限制硬编制上限、软招募比例、返还征粮队预留人数；`DefaultAIRecruitmentModel` 还会限制工资、费用与维护资金。某些情况确实应为0。

但现有日志缺少**最终瓶颈**：应在同一次 `BuildPlan` 结果上记录 `HardFreeSlots`、`SoftRecruitmentFreeSlots`、`ReservedSupplyEscortCount`、`DailyLimit`、候选数、按主拒绝原因聚合的0批准数与实际完成数。不得为了日志再次跑 `BuildPlan` 造成规划状态不同。

另一个待确认的设计点：`SettlementManpowerProductionBehavior.EnsureDailyProduction` 每日重置 `_dailyProfessionalOffers`，如果上一天的招募名额未被使用，候选不会自动长期保留；它可能是“当天训练能力不形成库存”的既定设计，而不是代码错误。核查需求后再决定是否要改生产进度，不在日志治理范围内擅自调整。

## F. P2 值得观察：封邑兵某日一次补充46名

行493：加隆托堡封邑兵一次补充46人，从当前推算的14人补足到60人。`FiefPartyReinforcement.WeeklyUpdate` 最新注释声称每周仅处理升级和返还批次，日常新增由 `SettlementManpowerProductionBehavior.EnsureDailyProduction` 完成。单日46人的原因可能是累计进度、长期积压或其他生产规则。本次日志**不足以证明生产速度失控**，但建议在生产调试中附“当日增量、此前累计进度、实际封邑编制、剩余额度”，观察两周实机曲线。

## G. P2 值得观察：读档任务失效与补兵往返

日志有10条“兵力任务恢复”，其中多数安全取消，之后又有部分 Party 重新规划回先前地点。旧任务取消本身已标明没有改动兵员，不能说发生了兵员损失。建议补充“为什么被判过期”的本地化细分原因（所属Clan变化、源兵种不可用、目标位置变化、任务对象失效、任务过期等），按读档**一次摘要** Info 输出；在 P0 身份修复后观察是否仍频繁回访但无法补兵。

## H. P3 看起来正常，不要误修

- 驻军最低人数已满足且不请求**外部增援**为预期行为；不能与领主**向驻军领兵**混为一谈。
- 俄尼拉连续招募2到4名职业兵说明自动招募链路至少对该定居点有效，并不能推出全部城堡都无问题。
- 运粮队发现敌人并绕行是正常的风险规避行为，只有反复绕路/卡死才需异常升级。
- `jawwal` 等非普通领主氏族的战争倾向读取失败可能为符合预期的桥接覆盖范围；应核对身份和调用范围，不能直接当作普通领主战争态度异常。
- 工资上限每日随着家族财富变化重算不必然是逻辑错误。要避免每个小额变化都刷 Debug。
