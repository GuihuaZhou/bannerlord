# ModifiedArmy AI 补员问题：纯日志诊断实施方案

> **文档性质：诊断增强方案，不是游戏逻辑修复方案。**  
> **审查基线：** `GuihuaZhou/bannerlord`，`main`，提交 `644ee32c3cb5b10ec31983f03c72fdd888b62690`（2026-10-28）。  
> **问题依据：** `ModifiedArmy(2).log` 中的弱小领主部队、重复补员规划、有限驻军调拨及征粮队预留等记录。  
> **适用范围：** `ModifiedArmy` 的 AI 兵力规划、补员任务协调、进城访问及调兵事务日志。  
> **状态：** 待实施；尚未修改仓库、编译或完成实机验证。

## 1. 目标与不可变更边界

### 1.1 唯一目标

**仅补充诊断日志，使下一轮实机日志能够明确回答“为什么 AI 领主部队已严重缺兵，却迟迟没有完成补员”。**

需要还原同一支 Party 的完整过程：

`每日兵力判断 → 候选兵源评估 → 任务建立/延续 → 是否发出移动命令 → 行军过程和命令变化 → 到达定居点 → 访问去重检查 → 实时调兵审批 → 实际转移/取消`。

针对日志中反复规划补员、却没有看到完成调兵记录的塔洛斯、济拉、泰伊斯等 Party，优先定位**首次未能执行的环节**，而不是根据缺失的成功记录推断其原因。

### 1.2 本次一律不修改的游戏逻辑

- **不**修复或改变 `PartyForceTaskCoordinator` 的移动指令重发、任务延续、取消、挂起或状态流转逻辑。
- **不**放宽 `AiRecruitRandomChance = 0.8` 的每日随机门槛；**不**为严重缺兵 Party 添加豁免。
- **不**修改 `AiForcePlanningModel` 的评分、候选排序、优先级或任务选择。
- **不**修改 `PartyForceCandidateService` 的兵源条件、文化权重、财务审批或可达性判断。
- **不**调整边境/内陆驻军最低留守标准（当前为 75% / 50%）；**不**改变征粮队预留人数的计算方式。
- **不**修改 `PartyExchangeBehavior` 的同 Party、同定居点、同日访问去重规则。
- **不**修改 `PartyVisitExecutionService`、`PartyExchangeModel`、`PartyExchangeService` 的调兵审批、执行、回滚与幂等性。
- **不**改变 Party 创建条件、出生地点、编制、工资、封邑兵规则及原版 AI 军事命令。
- **不**新增会影响存档兼容性的任务持久化字段，不引入新的补员任务、定时器或重试机制。

**允许的改动仅限：** 在现有计算或状态切换位置采集只读信息；输出中文日志；必要时增加不影响业务决策、且不写入存档的临时日志去重辅助信息。禁止因“记录日志”额外触发招募审批、兵员转移、移动指令、随机数消耗或可变状态更新。

## 2. 当前证据与待验证假设

| 观察/源码事实 | 已确认内容 | 尚不能断定的原因 |
|---|---|---|
| 沃斯特鲁姆实际调兵 | 阿庇斯两次分别申请 81 人、77 人，实际仅调入 3 人、9 人；两次城内驻军均降至 160 人 | 是否所有弱小 Party 都受同样容量限制 |
| 驻军最低留守 | 沃斯特鲁姆城内 160 人、外出征粮队预留 50 人，有效守军 210 人，恰等于最低留守要求 | 预留人数与实际作战能力的关系需另行评估，但本次不修改 |
| 反复规划 | 塔洛斯、济拉、泰伊斯等多次选择同一补员地点，日志中未见相应调兵完成记录 | 未发出移动指令、移动被覆盖、未抵达、到达未执行，均待追踪 |
| 规划中的随机门槛 | 最新源码中每支受管理 AI Party 每日按 0.8 概率进入招募规划；缺兵本身不会免除该门槛 | 该门槛对每支 Party 具体耽误了多少游戏日 |
| 现有任务的移动恢复缺口 | `ApplyLivePlan()` 在 `next == current` 分支直接返回；如果有效任务未获得移动命令，当前分支没有尝试补发 | 哪些实机任务实际进入该状态 |
| 移动目标变化 | 协调器发现有权控制的任务与 Party 当前目标不一致时，将任务取消 | 变化是原版军事接管、临时避敌、其他 Mod，还是别的原因 |
| 每日访问去重 | `PartyExchangeBehavior` 依 Party ID + 定居点 ID + 游戏日去重 | 是否发生“当日访问已消耗、补员任务在之后才建立”的情形 |
| 财政 | 部分严重缺兵 Party 的 Clan 有较高金币余额、Party 工资未接近上限 | 个别招募候选是否因具体资金审批失败 |

> **证据纪律：** 诊断日志必须写明“检测到的状态”和“当次拒绝原因”，不可把推断写成已确认的游戏事件。例如，只检测到 `TargetSettlement` 变化时，应记录“当前移动目标与任务目标不一致”，而不是直接断言“原版 AI 覆盖了 Mod 指令”。

## 3. 统一诊断设计

### 3.1 关联标识：复用现有字段，不改变存档结构

为同一任务的各环节构造**仅用于日志显示**的稳定追踪标识：

`部队 Party.StringId + 创建游戏日 CreatedDay + 版本 Version + 任务类型 Intent`

建议日志写成 `任务追踪标识：<PartyId>/<CreatedDay>/<Version>/<Intent>`。此值可在日志工具方法中动态生成，**不向 `PartyForceTask` 添加属性，不修改 `PartyForceTaskPersistence` 的保存格式**。对于尚未建立任务的每日规划，使用 Party ID + 游戏日作为当次评估标识。日志同时输出 Party 的中文显示名称，便于人工检索；标识用于跨记录精确关联。

### 3.2 日志级别及频率

| 日志级别 | 输出时机 | 建议内容 |
|---|---|---|
| `Info` | 任务建立、移动指令发出、抵达、成功或部分成功、取消或转为终止状态 | 能够重建任务生命周期的关键事件 |
| `Debug` | 每日兵力诊断、候选兵源汇总、当日未安排原因、任务被保留、同日访问去重、移动状态快照 | 诊断数值与分支条件 |
| `Warn` | 严重缺兵且连续无法推进、目标反复变化、到达后审批为零、状态明显不一致 | 值得优先排查但不代表确定存在程序错误的异常 |
| `Error` | 已捕获异常 | 中文摘要 + 独立技术异常详情；不改变异常原有处理路径 |

避免每帧输出：每日诊断最多每 Party 每游戏日一条；行军状态可每 Party 每游戏日一条，任务状态变化即时一条；候选拒绝理由只输出汇总及最有诊断价值的少量项目。**不增加影响任务逻辑的去重行为**。

### 3.3 统一中文用语

统一使用“领主部队”“驻军职业兵”“封邑兵”“雇佣兵”“兵力目标”“兵力缺额”“任务目标定居点”“最低留守要求”“有效守军”“外出护卫预留”“审批通过”“实际调入”“任务暂缓”“任务取消”等正式书面表述。

保留英文枚举名、ReasonCode 作为代码内部标识即可；**实际日志正文统一通过 `GameTexts.FindText()` 与 `submodule_strings.xml` 输出中文解释**。技术 ID、数字、`OperationId` 可作为追踪字段，不视作未汉化；异常堆栈允许保留原始技术信息，但应先给出中文事件摘要。

## 4. 逐文件日志补充要求

### 4.1 `ForceManagement/Behaviors/AiForcePlanningBehavior.cs`

**记录点：** `OnDailyTick()` 调用 `EvaluateParty()` 前后；当前 `LogPlan()` 输出处。

在不改变随机数调用次数或消费顺序的前提下，记录现有已经算出的：

- Party 中文名称、Party ID、游戏日、当前人数、目标人数、兵力缺额及缺额比例；
- 日常补员随机门槛的实际结果（通过/未通过）、现有需求评分与阈值；
- 当前是否存在任务、任务状态、任务目标及兵源类型；
- 当日决定的中文理由（维持现状、规划补员、继续任务、较高优先级命令、随机门槛未通过、无可用兵源等）。

**注意：** 当前需求评分由 `PartyForceCandidateService.BuildContext()` 生成，避免为输出日志重复执行模型或重新抽取随机数；可以将**现有上下文中的值**在调用链中以只读参数传给日志方法。

### 4.2 `ForceManagement/Services/PartyForceCandidateService.cs`

**记录点：** `BuildContext()` 与 `EnumerateCandidates()`，尤其是 `AddFiefCandidate()`、`AddProfessionalCandidate()` 的筛选位置。

对每次原本就会执行的候选判定，允许通过局部诊断计数汇总如下拒绝原因：

- 定居点正在遭受围攻；
- 无法获得有效导航距离；
- 定居点不是本 Clan 所属城镇或城堡；
- 封邑兵可批准人数不足；
- 缺少驻军或驻军安全可调人数为零；
- 驻军拥有士兵，但扣除在役封邑兵保护数量后可调人数不足；
- Party 招募模型审批人数为零；
- 雇佣兵市场不可用、距离或敌对关系不符合条件、购买及工资审批未通过。

**最重要的驻军快照字段：** 驻军城内人数、外出护卫预留、有效守军、最低留守要求、按防务规则可调人数、在役封邑兵保护人数、进入接收方审批的兵数、审批通过人数、Party 兵力缺额。

如果现有执行结果只能确认“审批为零”，不能确认具体是工资还是其他限制，日志就写“招募模型未批准”，**不得凭余额推断“资金不足”**。禁止为补充拒绝理由再次执行可能消费资源、提交预算或改变状态的审批。

### 4.3 `ForceManagement/Missions/PartyForceTaskCoordinator.cs`（优先级最高）

**记录点 A：`EvaluateParty()`**

- 判断 `current?.OwnsMovementOrder == true` 且实际 `TargetSettlement != current.TargetSettlement` 时：记录变更前后目标、`DefaultBehavior`、`ShortTermBehavior`、是否在军团、是否处于战斗、是否处于原版避敌状态、原任务状态以及最终被设置的取消原因。
- 任务因转移域冻结、已挂起等原因无法推进时：记录具体状态与现有原因码的中文解释。

**记录点 B：`ApplyLivePlan()`**

- `next == current` 时：记录“继续沿用现有任务”，并同时报告 `OwnsMovementOrder`、任务状态、`DefaultBehavior`、`TargetSettlement` 是否匹配。**只记录，不添加任何补发指令。**
- 新建任务但未满足下发移动条件时：逐一记录已有布尔条件（受管理 AI、军团、战斗、原版避敌），说明“本次未下达移动指令”；保留系统现有行为。
- 调用 `SetMoveGoToSettlement()` 时：输出“已向部队下达前往定居点的移动指令”；若需要确认引擎是否实际采纳，可在调用后**只读**当前 `DefaultBehavior` 和 `TargetSettlement` 并记录，不再发出第二次指令。
- `ReleaseOwnedMovementOrder()` 时：记录释放原因、是否仍是该任务持有的指令，以及系统原本是否执行 `SetMoveModeHold()`。**不改变释放时机或条件。**

**特别重要的状态诊断：** 如果出现“任务状态为 `Planned`，`OwnsMovementOrder = false`，每日继续沿用现有任务”，明确输出一条 `Warn`，描述这是**疑似任务未取得移动指令**，但**不自动修复**。

### 4.4 `ForceManagement/Behaviors/PartyExchangeBehavior.cs`

**记录点：** `SettlementEntered`、`DailyTickPartyEvent` 中 `EvaluateVisit()` 的现有入口及提前返回分支。

记录：

1. 进入定居点事件是否触发、是否是当前实际驻留定居点；
2. 是否处于 Mod 统一调兵模式；
3. 本 Party 在本定居点、本游戏日是否已经进行过访问检查；
4. 如因去重跳过，记录最近一次检查发生的游戏日及当前是否存在匹配补员任务；
5. 是否走攻城后驻军移交入口，还是普通补员任务入口。

**严禁：** 改动 `_lastEvaluationDay` 的写入位置、键、去重条件及 `return` 行为。日志应该放在现有判断前后进行只读说明，不能把“日志需求”变成新的访问重试功能。

### 4.5 `ForceManagement/Missions/PartyVisitExecutionService.cs`

**记录点：** `Execute()` 的任务匹配判断、进入执行分支及 `ApplyResult()` 前后。

统一记录：

- Party 是否真正位于任务目标定居点；
- 是否找到仍有效且目标匹配的任务；
- 任务意图、来源、追踪标识和事务 `OperationId`；
- 进入执行前 Party 现有兵力、目标兵力和缺额；
- 返回的 `TransferCommitStatus`、`ReasonCode`、`RequestedCount`、`ApprovedCount`、`TransferredCount`；
- 任务现有状态变化：完成、取消、需要恢复；
- 本次有无实际兵员转移。

注意 `PartiallyCommitted` 属于**事务已部分提交**，中文日志应明确写“部分完成”，不能描述成彻底失败。

### 4.6 `ForceManagement/Services/UnifiedRecruitmentExecutionService.cs` 与 `ForceManagement/Models/PartyExchangeModel.cs`

在**现有分支**只读记录：

- 初始申请人数及当前实时审批人数；
- 来源为职业驻军时的防务安全上限、可用普通士兵名册和在役封邑兵保护量；
- 调兵计划拒绝时已有的原因码及对应中文解释；
- 实际事务返回的人数、状态和原因；
- 驻军、领主 Party 转移前后的名册总人数（采用已有快照或现有可安全读取的数值）。

**禁止：** 为生成日志再次调用 `BuildPlan()`、重新扣款、重新提交预算、重新对账或再次发出兵员转移。

### 4.7 `ModuleData/submodule_strings.xml`

新增诊断字符串模板，确保：

- 诊断日志全部使用中文；
- 失败原因与具体约束对应，不用“其他原因”掩盖已知分支；
- 理由必须与可观察的状态一致；
- 任务追踪标识和必要数值保留在正文或末尾，便于检索；
- 原版枚举和内部技术原因码不直接作为面向玩家/测试者的主句。

无需重新组织全部现有本地化文本；只增加必要模板或补全当前缺失的中文原因映射。

## 5. 正式书面中文日志示例

> 下列内容为**期望输出示例**，不是 `ModifiedArmy(2).log` 已经发生的记录。人数及地点用于说明格式，实际数值必须由运行时读取，不能在代码中写死。

### 5.1 每日缺兵诊断

```text
[兵力诊断] 维扎耳托斯家族的塔洛斯的部队当前拥有18名士兵，目标兵力为102人，缺额84人。今日补员需求评分为0.82，最低规划门槛为0.25，随机门槛已通过。当前有效补员任务：前往费卡翁调拨驻军职业兵。任务追踪标识：party_talos/1825/3/Recruit。
```

### 5.2 任务已建立，但未下达移动指令

```text
[兵力任务] 塔洛斯的部队已建立前往费卡翁的补员任务，但本次未下达移动指令。原因：部队当前处于原版避敌状态。任务状态为“已规划”，尚未取得该任务的移动指令。任务追踪标识：party_talos/1825/3/Recruit。
```

### 5.3 继续现有任务但仍未取得移动指令（重点告警）

```text
[兵力任务警告] 塔洛斯的部队今日继续沿用前往费卡翁的补员任务，但系统记录显示该任务未持有移动指令，且当前实际移动目标与费卡翁不一致。本次仅记录状态，不主动更改部队命令。任务追踪标识：party_talos/1825/3/Recruit。
```

### 5.4 移动目标发生变化

```text
[兵力任务] 塔洛斯的部队原补员目标为费卡翁，当前移动目标已发生变化。现有任务的移动指令持有状态为“是”，部队当前行为为“前往另一目标定居点”，短期行为为“规避附近部队”，系统按现行规则取消原任务。本记录仅确认目标变化，不推定指令变化的发起者。任务追踪标识：party_talos/1825/3/Recruit。
```

### 5.5 驻军安全可调人数诊断

```text
[驻军调拨诊断] 沃斯特鲁姆城内驻军160人，外出护卫预留50人，有效守军合计210人，最低留守要求210人。按现有防务规则，本次可安全调出0人；阿庇斯的部队仍有77人兵力缺额。当前未形成可执行的驻军调拨额度。
```

### 5.6 抵达但未执行

```text
[兵力任务] 济拉的部队已进入坦姆努堡。系统已检查当前补员任务，但任务目标与此次访问不匹配，因此未执行驻军调拨。本次未发生任何兵员转移。任务追踪标识：party_zira/1825/4/Recruit。
```

### 5.7 当日访问去重

```text
[兵力访问诊断] 泰伊斯的部队今日已经在坦姆努堡完成过一次访问检查。系统按照现有每日去重规则跳过本次检查；当前存在前往坦姆努堡的补员任务。本次未重新审批或执行调兵。
```

### 5.8 部分调兵成功

```text
[统一调兵] 瓦罗斯家族的阿庇斯的部队在沃斯特鲁姆申请调入81名驻军士兵，审批后实际调入3人。城内驻军由163人减少至160人，领主部队人数由74人增加至77人。本次调兵部分完成，驻军已达到当前最低留守要求。
```

### 5.9 审批被拒绝

```text
[统一调兵诊断] 塔洛斯的部队已抵达费卡翁并提出驻军调拨申请，申请人数为84人，审批通过0人，实际调入0人。系统返回的拒绝原因是“驻军当前没有可安全调出的普通士兵”。本次未发生兵员转移。任务追踪标识：party_talos/1825/3/Recruit。
```

以上文本中涉及“抵达”“审批”“拒绝原因”等描述，**仅在对应事件和状态真实发生时输出**。若当前调用链没有足够信息支持某种详细原因，应保留更中性的中文描述，不得补造结果。

## 6. 为定位现有案例所需的最小日志链

对于塔洛斯、济拉、泰伊斯、厄洛倪克斯、弥那耳维娜、阿庇斯，下一份日志至少应能够按 Party ID 和任务追踪标识重建如下检查表：

| 环节 | 必须能回答的问题 | 缺失时应补的日志 |
|---|---|---|
| 兵力状态 | 当前多少人？目标多少？是否属于严重缺员？ | 每日兵力快照 |
| 是否进入规划 | 是否被随机门槛、需求阈值或高优先级行为挡住？ | 规划输入与拒绝分支 |
| 兵源 | 目标驻军可安全调出多少？封邑/职业兵/雇佣兵各有多少批准候选？ | 候选汇总及驻军防务快照 |
| 任务是否真实创建 | 是否形成 `PartyForceTask`？与旧任务是否同一个？ | 新建/沿用/替换/取消日志 |

## 7. 实施次序与验收

### 第一批：P0，先补齐任务生命周期（最有诊断价值）

1. `PartyForceTaskCoordinator.cs`：新任务创建、保留旧任务、未下达移动命令、移动指令发出、发现目标不匹配、取消/释放原指令。
2. `AiForcePlanningBehavior.cs`：当前兵力与目标、当日门槛、计划结果及任务追踪标识。
3. `submodule_strings.xml`：对应中文模板与原因映射。

**验收：** 下一轮运行可以确认塔洛斯连续选择费卡翁时，究竟是否持有有效移动指令；不能只看到反复的“决定前往费卡翁”。

### 第二批：P1，补齐抵达与审批

1. `PartyExchangeBehavior.cs`：定居点进入、已访问去重、实际检查触发。
2. `PartyVisitExecutionService.cs`：任务匹配、实际进入执行、提交状态和人数。
3. `UnifiedRecruitmentExecutionService.cs` / `PartyExchangeModel.cs`：现有审批环节拒绝理由与来源/目标人数。

**验收：** 对于已进入目标定居点的部队，能区分“任务不匹配”“被去重跳过”“审批为零”“事务拒绝”“部分成功”“全部成功”。

### 第三批：P2，补齐候选兵源归因及日志降噪

1. `PartyForceCandidateService.cs`：原有候选流程的只读汇总与拒绝分类。
2. 对持续缺员者保留每日综合日志；对重复、未变化的信息使用诊断性去重，且**不触碰业务去重**。

**验收：** 对沃斯特鲁姆能直接看到“城内驻军 + 外出护卫预留 − 最低留守”的计算；对费卡翁能看到实际审批能力，而不是只见可调人数表象。

### 不变量验证清单

- 开启诊断前后，相同战役状态下，**规划/决策规则、随机数使用次数及顺序不改变**。
- 不产生新的移动命令、不取消额外任务、不改变任何 Party 行为。
- 不调整士兵、伤员、驻军、封邑、俘虏、金币、粮食、工资、编制或征粮队预留。
- 不修改现有 `PartyForceTaskPersistence` 序列化格式与存档兼容性。
- 所有日志正文为正式书面中文，具备明确、可检索的 Party/任务追踪信息。
- `Info`/`Debug` 不在每帧无节制输出；不会因日志增强导致明显卡顿或日志体积异常。
- 日志异常不得影响原本业务分支；异常仅记录，不吞并或改变现有业务异常处理方式。
- 通过编译和游戏实机验证；**编译成功不等于问题已定位**。

## 8. 本轮完成后如何决定逻辑修复

本轮**只补日志并复测**。在下一份日志确认实际原因后，再另行提出逻辑修复：

| 日志证实的故障 | 后续可讨论的修复（**不属于本轮**） |
|---|---|
| 有效任务没有移动命令，且后续未重新下达 | 补员任务移动恢复机制 |
| 临时避敌反复取消正常任务 | 原版避敌与 Mod 任务协调 |
| 严重缺员被随机门槛反复跳过 | 危急缺员计划门槛豁免 |
| 已抵达但被访问去重跳过 | 访问与任务事务的去重边界 |
| 已抵达但驻军安全可调量为零 | 驻军最低留守与 Clan 兵力分配政策 |
| 有可用驻军但财务审批为零 | 创建/维护预算及工资限制审查 |
| 多支 Party 竞争同一驻军 | Clan 内兵源分配与优先顺序 |

**结论：** 本次提交应被定位为“AI 兵力规划与驻军补员任务诊断日志增强”，而非“AI 补员行为修复”。所有原有游戏决策必须保持不变。下一轮依托具备完整任务生命周期的中文日志，确定真正的失败环节后，再制定单独的业务修改方案。
