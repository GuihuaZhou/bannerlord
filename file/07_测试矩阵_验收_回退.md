# 联合验收与回退计划

## 交付不是单纯的“构建成功”

每个 Worker 必须提供：独立提交/PR、迁移文件清单、原有规则不变声明、涉及的存档与 Harmony 目标清单、实测结果、未测风险、可逆回退步骤。

仓库项目目标为 `netstandard2.0`，依赖 TaleWorlds 与 ModifiedPolitics 的游戏安装 DLL，`.csproj` 目前含多处 `D:\Steam\...` 本机路径。无法在 Worker 环境里引用 DLL 时，应明确“静态检查通过但无法实际编译”，不能伪称构建通过。建议集成方提供自己机器的 MSBuild 路径参数，移除硬编码路径可另行单独做工程化提交。

## 存档样本准备

推荐复制至少四份真实存档，禁止在唯一原始存档上测试：

- S1：最新版本正常运行，拥有驻军与封邑台账。
- S2：征粮队正在运输，带有库存、伤兵、任务目标。
- S3：新增援运输队在途，尚未送达或在返航。
- S4：旧版（若仍留存）含退役 `ReinforcementMission` 记录，用来独立评估 W1 兼容性；用户可决定不支持。

每次测试记录基准：战役日、当前阵营/氏族、领地驻军人数、外派护卫数量、封邑在役批次、粮食、金币、军饷、正在执行的任务。

## 静态检查与差异审核

1. `git diff --name-status <base>...HEAD` 审核文件范围；任何修改用户排除文件即退回。
2. `git grep -n 'PartyFinance' -- ModifiedArmy/ModifiedArmy` 检查迁移后是否还遗留旧引用。
3. `git grep -n 'ReinforcementMissionService\|IArmyMissionProtectionModel' -- ModifiedArmy/ModifiedArmy` 检查旧服务删除。
4. `git grep -n 'AddClassDefinition\|SaveableProperty\|SyncData(' -- ModifiedArmy/ModifiedArmy` 制作存档签名对照。
5. `git grep -n 'HarmonyPatch\|HarmonyPrefix\|HarmonyPostfix' -- ModifiedArmy/ModifiedArmy` 制作补丁签名对照；运行 `ForceEntryPatchAudit.LogActivePatches()`。
6. 薄 Patch 检查：搜索 `AddToCounts`、金币动作、大型随机筛选、状态更新是否仍位于 `Patches/`；经审批的例外须说明。
7. 进入游戏验证：静态搜索不能替代 Harmony 补丁应用结果、真实 SaveGame 加载和实际事务回滚测试。

## 合并顺序与冲突域

- W1 与 W2 可能同时碰 `ForceManagementFacade` 和 Contracts，合并时优先 W1，然后 W2 在新基线上 rebase。
- W3 改 `ForceManagementFacade` 和初始化，必须在 W1/W2 后集成。
- W4 改各业务 Patches，W5 改 `PartyFinance/Patches`，建议 W5 先移动后 W4 用新路径处理该 Patch。
- W6 拆大型 Behavior 必须在 W2/W3 核心状态稳定后执行；不同时开启涉及同一个 `SupplyPartyBehavior` 的第二位 Worker。
- `FiefSaveDefiner` 同时为旧补员 SaveId 和新运输组件注册，必须由单个集成 Worker 修改或统一审核。

## 回退步骤

- 每阶段独立 tag 或 commit；若存档加载失败，先回退该阶段而不是继续修改 SaveId。
- 若发现任意粮食/士兵凭空增减，停止游戏内继续保存，使用复制存档恢复复现。
- `PartyFinance` 移动可单独回退目录/命名空间；服务事务变化必须连同适配层整体回退，避免 Result 契约不匹配。
- 不因回退重写存档源文件或擅自改 Saveable 编号；禁止“修复”时清空已有在役批次。
