## 0. 任务摘要（直接给 Worker）

**业务目标**：只改变 **AI 自动征召封邑兵时的候选兵种配比**。对一次请求的 `maximumCount`，从当前封邑 `FiefPartyTemplate.TroopEntries` 读取具体根兵种及 `Weight`，按升级树把真实可用士兵归入各根兵种路线，采用稳定的整数权重分配并在库存不足时重新分配空缺，输出原来的 `List<RecruitmentCandidate>`。不再因为 `_fiefParty` 名册遍历顺序而偏向早出现的兵种。**不设计固定小队**。

**不可改变**：`MinimumFiefRecruitBatch=25`；AI 招募意图/选址、军事制度权重、资金/工资审批、免费服役天数、Hearth 动员、批次归还、玩家手动征召、封邑兵生产和升级逻辑；不增设 XML 项、不增设持久化对象或兵源池；不变更 Saveable ID/SyncData。

**首要修改文件**：

- `ModifiedArmy/ModifiedArmy/Fief/Models/PartyData/FiefPartyRecruitment.cs` — `BuildAvailableRecruitmentCandidates()`，并在该文件内做必要的 AI/玩家路径区分。

**调用方一致性必须核查**：

- `ModifiedArmy/ModifiedArmy/ForceManagement/Models/PartyExchangeModel.cs` — `BuildFiefMobilizationPlan()`；
- `ModifiedArmy/ModifiedArmy/ForceManagement/Services/PartyExchangeService.cs` — `ExecuteFiefMobilization()`。

出现下文所述「预览与提交名额不一致」时，允许在 *这两个调用点的最小范围* 内修复，而不是容忍新比例算法放大偏差。禁止扩大为整个调兵框架重构。

**本任务不授权提交、推送、开 PR**；Worker 在得到单独授权前只应提供本地变更和验证结果。

## 2. 精确需求与边界

**输入**：当前封邑已解析模板 `TroopEntries`、就绪名册 `_fiefParty`（含健康/伤员数）、目标 AI 允许的 `maximumCount`。

**输出**：`List<RecruitmentCandidate>`，每项 `(CharacterObject, AvailableCount, RecruitmentSource.Fief)`，总数不超过 `maximumCount`；同一个 `CharacterObject` 不得重复。

**规则 R1 — 来源**：只看 `_fiefParty` 中当前真实存在、`_fiefPartyTemplate.IsEnableTroop` 为 `true` 的兵种；不从模板凭空造兵、不从驻军/职业兵“借用”。

**规则 R2 — 权重**：读取 `_fiefPartyTemplate.TroopEntries` 中 `Weight > 0` 的根兵种。`Weight=0` 不参与此次配比，不能自动变成1；不加额外 XML 编制。

**规则 R3 — 升级树**：根兵种及其合法升级后代占用同一条根路线的配额。每名实际士兵只归属**一条**根路线：若根之间有祖先/后代重叠，优先归入**最近的匹配根**（距离升级后代更近）；同距离按模板条目顺序，最后以根 `StringId` 稳定破同分。遍历升级树必须有 visited 集合以防循环。不可沿用历史全局 SoldierType 分类替代精确模板。

**规则 R4 — 健康人数**：候选 `AvailableCount` 应是 `max(0, element.Number - element.WoundedNumber)`，排除英雄、零数、不合法兵种。实际提交阶段也必须核实“健康人数被移走、伤员保持不变”这一不变量；若原生 `TroopRoster.RemoveTroop()` 的实际语义不能保证，则必须先核实游戏 API 并针对这条路径做最小安全处理，绝不能让预览健康、执行却扣掉伤员。

**规则 R5 — 分配比例**：目标人数 `N = min(max(0, maximumCount), 所有合格健康兵总数)`；先按各根权重分配整数名额，使用**最大余数法**，同余数按 XML 条目顺序破同分；不依赖字典枚举或名册顺序。

**规则 R6 — 库存不足**：某根实际健康库存不足其目标名额时，截到库存上限；余下缺额按**仍有剩余库存**的根权重再次分配。重复直到名额用尽或所有路线库存耗尽。不能将名额流向 `Weight<=0` 或模板外兵种。

**规则 R7 — 根内部选兵**：先按兵种 `Tier` **降序**、再按 `CharacterObject.StringId` **升序**取健康士兵，以保持当前 AI 高 Tier 优先取兵的语义；不要改动全局 `DefaultAiTroopRecruitmentModel.GetPriority()`。若有同兵种多条名册记录，先合并其健康人数再分配。

**规则 R8 — 策略范围**：只对 **AI 自动封邑征召**启用权重分配。`BuildPlayerFiefRecruitment()` 所用的玩家**自动征召**继续按原有名册来源/额度方式构造候选；`RecruitManualSelection()` 更不得改变。可仅在 `FiefPartyRecruitment.cs` 为 `BuildAvailableRecruitmentCandidates` 增加显式策略参数（如 `bool useTemplateWeights`）或小型本地辅助函数；预览和提交两处都按同一 `targetParty.LeaderHero.Clan` 判断 AI/玩家。不要靠全局状态推断调用方。

**规则 R9 — 审批权威**：配比只是候选阶段的**偏好目标**。之后仍由 `RecruitmentModelManager.Model.BuildPlan()` 综合上限、工资与长期财政决定最终招募；若审批削减某个高 Tier，比例可能偏离模板。这次**不**改统一招募模型、不二次循环新增未经审批候选；对比率采用“尽力满足，而非绝对保证”。

**规则 R10 — 无副作用**：预览函数与配比函数不得更改 `_fiefParty`、Party、Hearth、Clan 预算、`FiefServiceBatch`、随机数状态；对相同模板/库存/请求得到完全相同的 `CharacterObject → Count`，即使 `_fiefParty.GetTroopRoster()` 返回顺序改变。

## 3. 建议实现算法（可直接转 C#）

在 `FiefPartyRecruitment.cs` 中保留当前私有函数（可添加一个策略入参），实现为只读候选规划，必要时提取**私有**辅助函数，不增设全局状态和服务。

```text
BuildAvailableRecruitmentCandidates(maximumCount, useTemplateWeights):
    if template == null / roster == null / maximumCount <= 0: return empty
    if !useTemplateWeights:
        return existing-player-candidate-behavior(maximumCount)

    roots := template.TroopEntries
        .Where(entry.Troop != null && entry.Weight > 0)
        .OrderBy(XML entry ordinal)
    if roots empty: return empty

    stock := read *all* _fiefParty troop elements once
        valid only if IsEnableTroop(troop), troop non-hero
        healthy = max(0, Number - WoundedNumber)
        merge duplicate CharacterObject health into one counter
    if stock empty: return empty

    membership := map every stock troop to exactly one eligible root:
        shortest ancestor-to-troop upgrade path; deterministic tie-break
        ignore stock that maps to no positive-weight root
    groups := each root { weight, stock by CharacterObject, remainingCapacity }

    N := min(maximumCount, sum(group.remainingCapacity))
    allocations[root] := 0
    remaining := N
    while remaining > 0:
        active := groups where remainingCapacity > 0 and weight > 0
        if active empty: break
        roundQuota := HamiltonLargestRemainder(remaining, active weights,
                                                tie: XML ordinal then root ID)
        for each root:
            take := min(roundQuota[root], root.remainingCapacity)
            allocations[root] += take
            root.remainingCapacity -= take
            remaining -= take
        assert progress or fail safely (not infinite loop)

    for each root in template order:
        quota := allocations[root]
        for each child troop in group.sortedBy(Tier desc, StringId asc):
            taken := min(quota, stock[child])
            if taken > 0: candidates.Add(new RecruitmentCandidate(child, taken, Fief))
            quota -= taken
            if quota == 0: break
    return candidates
```

**算法注意事项**：

- `HamiltonLargestRemainder()` 对 `remaining * weight / sumWeight` 可用 `long` 计算整数商与余数；优先使用整数余数比较避免浮点误差；按余数降序、XML 条目序升序补齐剩余个位。
- 避免在 `while` 中直接按 `Dictionary` 自带顺序分配。
- `RequiredBarracksLevel` 只用于当前**生产**筛选；征召已入库士兵时，不应因为兵营等级下降就抹去合法现存兵。身份仍由 `IsEnableTroop` 决定。
- **重复根 ID**要合并权重或作为无效模板报清晰诊断，不能让同一角色重复进入两个候选；倾向按 `StringId` 合并权重并保留最早 XML 顺序。
- 审批后低于25人的规则维持既有返回0；除非有真实可执行的审批数量，不得仅因为库存>=25就宣称可征召。
- 可以保留“没有任何正权重有效根兵种 ⇒ 返回空候选”的安全行为，**不要**回退到“顺序拿兵”，否则再次引入偏置。

### 3.1 纯权重算法示例（假定五条根兵种均有效且库存充足）

按固定显示顺序：骑士1、轻骑1、封臣步兵2、普通步兵3、征召弩兵2。

| 请求 N | 骑士 | 轻骑 | 封臣步兵 | 普通步兵 | 弩兵 | 合计 |
|---|---:|---:|---:|---:|---:|---:|
| 25 | 3 | 3 | 6 | 8 | 5 | 25 |
| 40 | 5 | 4 | 9 | 13 | 9 | 40 |
| 45 | 5 | 5 | 10 | 15 | 10 | 45 |

说明：N=25 和40存在余数并列，依模板节点顺序破同分；当前三份瓦兰迪亚模板的节点顺序不同，但上述两例的最终兵种数量在其现有相对顺序下仍可一致。测试要直接从每份真实模板取顺序，而不能硬编码例子中的排序。

**缺货示例**：请求40，五路库存足量，唯独骑士路线只有2名；第一轮理论分配为 `[5,4,9,13,9]`，骑士缺3名；按仍有库存的四条路线权重重新分配后，最终为 `[2,4,10,14,10]`，合计40（假设各路线库存均允许且未执行财务裁剪）。

### 3.2 零配额或升级树重叠

- 若正权重根 A 是根 B 的祖先，B 的库存先归入最近根 B；剩余 A 家族兵归 A。两根不重复计数。
- 仅靠 `IsEnableTroop()` 能证明封邑身份，**不能**推导其权重归属；必须使用具体升级树。
- 不允许把一棵树中 B 的后代同时作为 A 和 B 两组的库存进行征召。

## 4. 交易层一致性：必验收项（可能需要第二处极小修改）

这是本方案最容易遗漏的地方。当前运行链是：

```text
PartyForceCandidateService.AddFiefCandidate
    -> PreviewFiefRecruitmentApprovals(target.GapCount)
    -> 规划前可行数量
UnifiedRecruitmentExecutionService.ExecuteFief(requested=GapCount)
    -> PartyExchangeModel.BuildFiefMobilizationPlan(context.RequestedCount)
    -> plan.SourceToDestination[CharacterObject -> count]
    -> PartyExchangeService.ExecuteFiefMobilization(...)
         当前代码：RecruitFiefTroopsFromSettlement(source, destination,
                                  plan.SourceToDestination.TotalCount)
              -> 再调用 BuildAvailableRecruitmentCandidates(maximumCount)
              -> 再做财务审批及实际入伍
```

**潜在缺陷**：预览请求是40，因财务限制最终批准25人；执行函数重新以25人做**一轮新的配比**，于是原计划可能是 `[5,4,9,7,0]`，实际改为 `[3,3,6,8,5]`（示意），总数同为25但**兵种完全不同**。当前 `ExecuteFiefMobilization()` 只比总人数，不比具体 manifest，可能错误报告 `Executed`。

**Worker 的最小修复要求**：

1. 在调用权威征召时，应保留首次审批的**原始请求语义**，避免把“批准数”作为新一次配比的请求；检查 `PartyExchangePlan.RequestedCount`（或其源头的 `context.RequestedCount`）是否就是对应字段，不能盲改。
2. 在变更任何资源之前，使用现有只读 `FiefPartyManager.PreviewFiefRecruitmentApprovals(source,destination,原始请求数)` **重新生成候选批准清单**，逐 `CharacterObject`、逐数量对比 `plan.SourceToDestination.Troops`；若不相等，拒绝/重规划，不得仅比总人数。预览过程本身不得扣 Hearth 或预算。
3. 若现有审批执行入口仍重新规划，须证明在快照、资金及状态未变化时预览/实际得到**完全相同** manifest；若存在无法保证的窗口，应采用既有最小交易入口传递核验过的 manifest，且在实际提交前做合法性、预算、健康人数及容量再验证。切忌直接绕开 `RecruitmentModelManager`。
4. 若这一补丁需要改动超出 `FiefPartyRecruitment.cs` 与 `PartyExchangeService.cs`（必要时少量触及 `PartyExchangeModel.cs`）且无法做到事务安全，**标记 BLOCKED，解释并提交最小修复提议；不要扩大成调兵框架重写**。
5. **改动前已有的独立风险**：`RecruitTroopsToParty()` 先执行 `TryMobilize`（Hearth 预留），再逐项改名册并 `CommitRecruitment`，对局部数量变化未显式做全量回滚。本期只允许必要的最小保护，但验收绝不可忽略 Hearth/名册/预算/`FiefServiceBatch` 的守恒。不要因为本期主要是候选算法就宣称事务无需检查。

## 5. 实施顺序（独立可验证）

### Phase A — 固定基线及配置资格

1. `git rev-parse --show-toplevel`、`git branch --show-current`、`git rev-parse HEAD`、`git status --short`；发现非本人改动立即保留、不覆盖。
2. 阅读三级规范；审查代码调用链与当前版本号，确认上述路径未被再次移动或改写。
3. 验证具体模板 `TroopEntries` 实际解析结果及 `vlandian_feudal_infantry` 问题，记录事实与阻断状态。
4. 记录旧预览/提交行为的测试数据（同一库存、不同名册顺序、不同请求人数、不同预算）。

### Phase B — 最小候选改动

1. 在 `FiefPartyRecruitment.cs` 使 AI 候选走按模板根路线的稳定权重分配；玩家自动征召保持旧行为；手动征召不动。
2. 对空值、零权重、缺库、重叠升级树、伤员、重复角色执行完整合法性检查。
3. 预览 / 提交都调用**同一个无副作用候选函数**，不为二者各复制一套算法。
4. 添加极少量可定位的 Debug 诊断（模板 ID / 封邑 ID / 请求数 / 每根库存和分配 / 审批数 / 限制原因），遵循本项目既有 `RecruitmentLogFilter`；不在高频全图路径逐兵刷日志，也不在 C# 写硬编码中文玩家通知。

### Phase C — 交易一致性保护

1. 对照 §4，确保同一事务在预览与提交中沿用同一个请求语义，校验具体兵种 manifest。
2. 对拒绝/变更的交易明确返回原因，不得悄悄改为另一份仍然“总数相同”的候选。
3. 检查实际转移健康士兵与现有 Hearth/预算/服役批次守恒；如必须额外改动，严格限定在当前封邑动员路径，另列行为差异。

### Phase D — 测试与交付

1. 下表全部执行，记录可复现实测、实际输出和 PASS/FAIL/BLOCKED。
2. 审查 `git diff --check`、`git diff --stat`、`git diff`，说明实际修改文件/方法，没有任何 XML/存档/经济参数无关改动。
3. 执行 `dotnet build .\ModifiedArmy\ModifiedArmy.sln -c Release` 和 `ModifiedArmy/tools/Test-ArchitectureReleaseGate.ps1`；可执行时使用 `ModifiedArmy/tools/Invoke-ReleaseValidation.ps1` 及运行时证据脚本。请在本地先读取参数及所需依赖。
4. 游戏内/存档读写类测试无真实证据一律填 `BLOCKED`，不得把编译 PASS 冒充实机 PASS。

## 8. Worker 最终交付格式

1. **基线**：仓库、分支、开始和结束 HEAD SHA，`git status --short` 与是否触及他人改动。
2. **改动**：逐文件/方法列出差异及为何必要；说明玩家路径是否完全不变。
3. **配比**：列出一份真实 XML 模板实际解析后的根、权重、可用库存、分配结果、财务审批、最终招募的对照表。
4. **预览/执行守恒**：单次交易的每兵种计划值与实际值、健康/伤员、Hearth、Clan 预算、批次人数与 ID。
5. **测试**：T01–T18 的 PASS/FAIL/BLOCKED、证据路径、构建与脚本实际输出；不要省略阻断点。
6. **遗留风险**：特别报告 Vlandia `vlandian_feudal_infantry` 注册缺失、原生 `RemoveTroop` 伤员处理与事务回滚问题的实际处理状态。
7. **仓库动作**：未获授权不 commit / push / PR。

**Worker 执行原则**：先保证“按真实模板配比、按真实库存取兵、经现有财政审批、最终逐兵种账目一致”，再考虑任何额外优化。若预览/提交一致性或动员守恒无法被验证，不得用“只动了一个函数”作为通过依据。
