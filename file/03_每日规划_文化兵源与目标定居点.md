## 1. 目标

将 `Recruitment/Behaviors/AiRecruitmentBehavior.cs` 转为 `AiForcePlanningBehavior`：**每日作一次状态决策，补员时评估所有兵源+目标定居点候选，生成任务和移动指令，绝不直接操作Roster**。WarRest评分在第04文档提供；本任务先完成战略通用机制。

## 2. 现有流程与具体缺陷

`AiRecruitmentBehavior.OnDailyTick()`当前：按Kingdom/Clan/WarPartyComponent遍历 → 冲突任务检查 → 同Clan多目的访问 `FindBestMultiPurposeSettlement` → `TryDispatchPeaceDemobilization` → 招募随机门控与NeedScore → `CalculatePreferredSource` → 分兵源搜索 `FindBestXSettlement()` → `SetMoveGoToSettlement`。

`AiSettlementRecruitmentPatch.cs`又在原版`CheckRecruiting`内独立读取 `GetRecruitmentDecision`并**实际征召、取兵、购买雇佣兵**，是第二决策执行入口。

`IsPartyCurrentlyOnRecruitmentTask()`仅靠`TargetSettlement`和Clan自有城市判断，可能误判其他系统指令；`RecruitmentCampaignBehavior.OnBeforeSettlementEntered`原版可能多次调用`CheckRecruiting`，不能把这里当新统一执行入口。

## 3. 每日任务决策模型

```text
检查生存/阵营/受保护任务/危险/当前持有的Mod任务
→ 读取PartyForceTargetModel唯一兵力目标
→ 正式战争：评估WarRestPolicyModel（第04）
→ 计算普通Recruit必要性（现有NeedScore保留合理部分）
→ 在Maintain、Recruit、WarRest、Suspended间选择
→ 对必要任务选择定居点并建立PartyForceTask
→ Behavior仅发出可安全覆盖的路由命令
```

`Maintain`不是“强制驻留”；应恢复/交回原版正常战略AI。`Suspended`不应删士兵，也不能覆盖原版Army、围城、追击、守城增援等更高优先级命令。

已有Mod任务仍有效时优先继续；只有策略变化、任务不可行或军事优先级改变才切换。不允许当天重复更换目的地，禁止重复下达相同移动命令。

## 4. 文化偏好与联合可行性

### 4.1 文化来源

保留 `CalculatePreferredSource()`当前文化基础权重：`GetAiCulturalPreference(culture)`；情境修正 `GetAiSituationalModifier(peace/war/siege/broke/critical)`，归一化后分配 `Fief/GarrisonTransfer/Mercenary` 相对偏好。

现有文化元数据：`militaryConfig.xml` 与 `common/MilitaryConfig.cs`。`Fief`偏好和`Professional`驻军偏好不互换身份；本轮不改文化权重，不将所有文化压成统一“最近定居点”权重。

### 4.2 新候选

`RecruitmentDestinationCandidate`建议记录：`Settlement`, `RecruitSource`, `EligibleCount`（可审批数）、`GapCovered`, `CulturePreference`, `CultureMatchFactor`, `TravelCost`, `RouteRisk`, `EconomicImpact`, `FeasibilityReason`, `Score`。

枚举时执行两阶段：

1. **硬可行性**：Ownership/敌对关系/城市或城堡类型、路线可达/危险、来源库存、可批准人数、最低Fief批次、Party容量/工资/金钱、驻军安全下限、封邑批次可用。返回0者不得入选。
2. **软排序**：文化偏好（独立且重要）× 实际补员覆盖率及文化匹配，再与行军距离/风险/额外成本协调。实际公式须有可测试的固定参数和稳定排序tie-break；禁止无条件按最多士兵或最近目的地排序。

同一Settlement可产生多候选（Fief、Garrison、Mercenary）；可以允许有限联合收益来避免频繁跑城，但不要在路由评分时保证到达后每个兵源都执行，最后还是由Model根据最新状态审核。

### 4.3 避免预测与实际分歧

只读预览不得提交Clan招募预算、Hearth动员或名册变化。旅途中库存可能变化，抵达时必须重新生成审批；失败任务可在下一个Tick重新选址，避免同一瞬间无限重试。

## 5. 任务状态与持久化

`PartyForceTask`记录：`PartyId/ClanId`, `Intent`, `Destination`, `PreferredSource`, `CreatedDay`, `LastValidatedDay`, `Status`, `Reason`, `Progress`, `OwnsMovementOrder`。定居点对象存档引用必须使用游戏认可的类型定义，兼容既有保存。

建议过程：`Planned → Traveling → Visiting/Executing → Completed | Cancelled | Suspended`。Status与Intent分离；目标到达不等于任务完成（WarRest可多日）。

每日检验`TargetSettlement`是否仍对应**自己**发出的任务；若原版改变了AI命令，不要误当Mod仍在控制移动。取消任务时仅撤销自己拥有的命令；避免`SetMovePatrolAroundPoint`覆盖原版正在执行的更高级命令。
