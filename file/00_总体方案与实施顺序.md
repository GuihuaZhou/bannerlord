## 0. 结论与整改原则

**保留已经完成的工作，不整体推翻重构。** 现有按业务域分组、`PartyFinance → PartyManagement/Finance`、多数薄 Harmony Patch、新增援运输与已实现的 Campaign 引用切换都应保留。整改焦点：W2 的事务状态与异常恢复闭环、W3 的跨存档生命周期和恢复顺序、W6 的真实职责拆分、少量 W4 遗留与 W7 依赖治理。最终仍是**一个 ModifiedArmy DLL**。

验收判据不是“创建了若干 Service”，而是：①每一种资源只有权威写入路径；②日志、保存、恢复与调用方消费同一结果契约；③Behavior 只拥有事件与必要存档入口；④纯计算无副作用；⑤用户既有游戏规则与序列化身份不变。

## 1. 整改后目标调用关系和状态所有权

```text
Main / CampaignReadyBehavior（保留奖励）
       │ 每局建立/切换运行时服务，读取旧存档后进行恢复
       ▼
ForceManagementFacade.Current（保留兼容入口）→ Campaign scoped services
       │
       ├─ Behaviors（只接 CampaignEvents、必要 SyncData、转发）
       │    ├─ AiForcePlanningBehavior ─────► PartyForceTaskCoordinator
       │    ├─ PartyExchangeBehavior ──────► PartyVisitExecutionService
       │    ├─ SupplyPartyBehavior ────────► SupplyDispatch/Route/Cargo/Recovery
       │    ├─ FiefPartyManager（原存档权威入口）► FiefLedger/Reconciler/Return
       │    └─ GarrisonRecruitFromPrisonersBehavior ► Recruitment services
       │
       ├─ Models / Policies（只读输入、输出计划/审批）
       ├─ Domain Services（真正提交 roster/金钱/粮食/封邑服役批次）
       ├─ Persistence adapters（原有存档键和旧格式保持，新增记录仅作附加）
       └─ Infrastructure/Transactions（通用快照/守恒/补偿工具，不放业务规则）

Harmony Patch → 业务 Policy/Service；不在 Patch 内另维护真实资源。
跨模组 WarDispositionAdapter → ModifiedPolitics（需先决定强制/可选依赖）
```

| 状态类别 | 应由谁拥有 | 保存/重建规则 |
|---|---|---|
| `FiefPartyManager._fiefDataMap`、动员户数、ServiceBatch | 原 `FiefPartyManager`、原 `FiefPartyData`（权威） | 保持现有 SyncData/SaveDefiner 编号，服务仅操作原记录 |
| `AiForcePlanningBehavior._savedTaskRecords` | 原 Behavior（序列化入口） | `modifiedarmy_force_task_records_v1` 不变；协调器使用运行时重建对象 |
| 已提交 OperationId、RecoveryRequired 操作 | 所属 Campaign 的事务协调器 + 受支持的持久化入口 | 已落盘的历史操作不能读档后重放；异常待恢复应冻结相关任务/资源；须限定 journal 增长、禁止随意丢失尚可重放的 ID |
| `ForceManagementFacade` 的模型和服务 | 当前 Campaign 的 Scope | Campaign 对象变化就替换；不得保留旧世界对象引用 |
| `SupplyPartyBehavior._nextDispatchTimes` | 原 Behavior（现有存档） | 继续使用原保存键；路线日志/节流纯运行时字段按 Campaign 重建 |
| `WarRestPlanningService._progress`、warning suppression | Scope/当前 Campaign 运行时 | 按天/换档显式复位，不能污染另一个存档 |

**不允许**“把 Fief 的兵员人数复制到新的永久 Ledger，形成两个权威账本”。也不要求把 Saveable 类型物理移动到新目录；服务身份与序列化类型身份是不同问题。

## 3. 各阶段具体修改方法

### S0：基线与交付测试资产（只读阶段）

1. `git fetch origin; git rev-parse HEAD; git status --short`，确保干净；若 HEAD ≠ 本文 SHA，输出 `git diff <本文SHA>...HEAD -- ModifiedArmy` 的变化列表并重新定位。
2. 列出全部事件订阅、Harmony Patch 签名/返回行为、`SyncData` 键、Saveable 类型/字段、`static` 和实例状态，以及实际资源写入（`AddToCounts`、`GiveGoldAction`、`ChangeMercenaryCount` 等）。
3. 为关键方法生成原地行为契约：输入、前置权限、名册/金币/粮食/状态变化、错误处理、调用方、是否入档，禁止凭空改规则。
4. 复制测试存档 S1 常规、S2 征粮在途、S3 增援在途、S4 旧增援兼容（可选）；创建备份。没有现成的就诚实标不可测，不得造假。
5. 生成 `baseline/` 下测试表、权限矩阵、Patch 矩阵、状态归属表；不得修改用户排除文件。

### S1：W2 调兵事务闭环（优先级 P0）

**当前代码定位**：`ForceManagement/Services/PartyExchangeService.cs` 的 `_completedOperationIds`、`Execute/Validate/ExecuteRosterTransfer/ExecuteFiefMobilization/ExecuteFiefReturn`；`ForceManagement/Contracts/UnifiedForceContracts.cs` 的 `TransferCommitStatus`；`ForceManagement/Behaviors/AiForcePlanningBehavior.cs::ExecuteAtSettlement`；`ForceManagement/Services/UnifiedRecruitmentExecutionService.cs::ExecuteMercenary`。

1. 保留现有五态枚举和 `Executed` 兼容属性，明确 `HasCommittedChanges` 不等于精确实际到达人数。所有消费点必须根据状态分类：`Committed`→结束 attempt；`PartiallyCommitted`→结束当前 attempt、保留实际变化、创建**全新审批/全新 ID**补缺；`Rejected/RolledBack`→无已确认提交，按原策略另行规划；`RecoveryRequired`→冻结关联任务，持久化异常现场标识，等待重新对账或人工介入。不要仅把后四种映射为 `Cancelled`。
2. 对普通名册操作保持现有权限/快照/伤员/双方守恒/反向补偿；逐项核查 `AddToCounts` 异常发生于源端扣除后、目标端增加后时的补偿顺序，`RecoveryRequired` 不能返回虚假的精确转移数；将来源/目标的可观察快照、错误码及冻结域输出给恢复处理。
3. 对封邑动员/返乡：允许权威服务只返回真实执行人数和批次变化；记下已提交 `OperationId` 防止再次提交同一操作；不额外凑数、不复制名册、不重复动员户数。
4. 保留 `PartyExchangeService` 为当前 Campaign 单例，新增小型 `TransferOperationJournal`（可先服务内部记录），设计其可安全存档的最小投影，**先验证 SaveSystem 支持再选存储格式**。历史保存键不变；新增键需独立设计版本，加载后只重建索引、不重新执行历史提交。对不可确定的 `RecoveryRequired` 采用只读对账 + 阻止同任务自动写入，不通过自发修改名册“修复”。
5. 雇佣兵执行 `ExecuteMercenary` 目前直接扣金币/市场/加名册/预算并未使用传入的 `operationId`：单独增加已提交 ID 防重与前后状态核对，处理多资源提交部分失败的恢复；不能未经规则分析强行用封邑兵的调兵模型替换购买路径。
6. 对调用图执行全文检索 `.Executed`, `.HasCommittedChanges`, `.TransferredCount`, `.Status` 和 `OperationId`；尤其 `AiForcePlanningBehavior`、`PartyExchangeBehavior`、`UnifiedRecruitmentExecutionService`、`TroopTransferService`、`ReinforcementTransferService`。不要一次修改所有转移算法；先划清“哪些经统一事务引擎，哪些权威于专有业务服务”。
7. 增加测试桩/可重复的纯逻辑测试：完整 30/30、部分 20/30、0/30、陈旧快照、重复 ID、普通回滚、无法回滚、封邑返乡、雇佣兵扣款一次；加 S1 报告。**不能因写了单元测试就宣称实机崩溃恢复已验证。**

**阶段完成门槛**：不再有把 `RecoveryRequired` 静默按 `Cancelled` 重新规划的路径；同一已提交 ID 重放不会再次写资源；真实 roster/伤员和封邑批次不凭空增减；修改范围与契约可审计。

### S2：W3 Campaign 生命周期闭环（P0）

1. **保留已有实现**：`ForceManagementFacade.Current` 已用 `_campaign` + `_current` 按 `Campaign.Current` 换实例，并执行 `GarrisonRecruitmentCapacity.ResetRuntimeDiagnostics`、`NewSettlementFoodModel.ResetRuntimeState`、`ClanRecruitmentBudgetManager.ResetRuntimeState`、`BasicTroopGroupManager.Clear`，这是基础，**不因没有 Bootstrap 目录便重做**。
2. 列清状态所有权：`PartyExchangeService._completedOperationIds`、新事务记录、`WarRestPlanningService._progress`、`WarDispositionBridge.ReportedFallbacks`、`GarrisonRecruitmentCapacity` 静态警告集合、`SupplyPartyBehavior` 各类节流字段、`AiForcePlanningBehavior._tasks/_savedTaskRecords` 等。标记持久化/重建/纯诊断/每日复位。
3. 必须建立一条明确的恢复协议（可新建 `CampaignRecoveryCoordinator`，或在原 Behavior 组合实现）：`SyncData` 读档→所有依赖的 Saveable/行为完成恢复→封邑在役索引重建→运输/征粮/AI 任务验证→事务冻结项重建→标记 Ready。调查 Bannerlord 事件实际顺序，不能自以为某个 `OnGameLoaded` 一定晚于所有 `OnGameLoadFinished`。

5. 编写 A→B→A 同进程测试；同 ID/同名称/同日的不同世界不冲突；读档后不重复订阅和初始化 XML；运输队正常恢复。

**门槛**：存档身份不变、跨档状态互不污染、旧事务冻结状态不会丢失、没有二次奖励。

### S3：W6-B AI 规划 Behavior 真正拆分（P1）

- 目前 `AiForcePlanningBehavior` 既保存任务、做每日规划、路线所有权、到达招募、战时休整/复员、日志。拆分要以职责而非行数为准。
- 新 `ForceManagement/Missions/PartyForceTaskCoordinator` 管 `EvaluateParty`、`ApplyLivePlan`、`PruneTerminalTasks`、执行结果状态、路线所有权。任务清单可以仍由 Behavior 保存；Coordinator 不创建第二份持久任务状态。
- `PartyForceTaskPersistence` 负责将运行时任务映射为原 `_savedTaskRecords`；**原 `modifiedarmy_force_task_records_v1` 键及字段/分隔符不变**；加载后只重建临时引用和合法性，禁止回放已提交的资源动作。
- `PartyVisitExecutionService` 接收一次合法到达/驻留操作，区分常规捐兵、封邑/驻军/雇佣兵补员、战时休整、攻占后捐兵、和平复员，委托既有领域执行 Service；不用“为了统一入口”更改选兵规则。
- `PartyExchangeBehavior::EvaluateVisit` 与 `AiForcePlanningBehavior::ExecuteAtSettlement` 明确操作所有者；同 party+settlement+day 去重用于避免双事件，**事务 OperationId 去重与日门禁分开**。如果一次尝试被拒绝，该日是否允许重试由原游戏规则及明确的回归用例决定，不默改。
- 新 Behavior 应只接事件、委托协调和序列化；老公开方法可以作为兼容代理存在。

**门槛**：S1 的五态处理不被拆分回退；T01–T07/T14；相同输入的 AI 目标、随机门禁、行动时机等价。

### S4：W6-A 征粮 Service 化（P1）

当前 3 个 `partial class SupplyPartyBehavior` 文件：`Garrison/Supply/SupplyPartyBehavior.cs`、`SupplyPartyProvisioning.cs`、`SupplyPartyTransaction.cs`；新增 `Models/SupplyProvisionModel.cs` 已把一部分估算独立出来。

1. 固定事件入口、所有实例状态、组件 Saveable 字段与日志模版；先录制路线/库存行为基线。
2. `SupplyDispatchService`：提供合法派遣评估、候选选取和冷却策略；Behavior 只按 Tick 调用。必须保持 `CanActuallyDispatchLocalForaging` / `HasActiveLocalForagingMission` 对跨城援粮是否触发的原判断。

## 4. Worker 使用和交接规则（本次失败最需要改变的部分）

**绝对不要把本方案所有阶段交给一个 Worker，要求在同一次任务中直接全部实施并一次提交。** 可以首次阅读总方案形成全局依赖认识，但每次实施仅领取一个 `S1`…`S8` 工作文件。在完成本阶段 Commit 与验收报告后，新会话读取“总方案 + 当前阶段 + 上阶段交接报告 + 当前代码”，无需注入此前聊天的全部调试记录。

每阶段开工输出（不得跳过）：

```text
BASE_SHA：<git rev-parse HEAD>
STATUS：<git status --short>
OBJECTIVE：<本阶段具体不变量和验收编号>
IN_SCOPE：<允许修改的文件/方法>
OUT_OF_SCOPE：<本阶段禁止碰的模块和保护文件>
STATE_CONTRACTS：<涉及的 SaveId / SyncData / Harmony target / 操作权限>
TEST_PLAN：<可执行测试 + 必须用户手动验证的测试>
```

每阶段结束输出（**没有验收材料不得宣称完成**）：

```text
PHASE：Sx
BASE_SHA / NEW_SHA：...
CHANGED_FILES：git diff --name-status BASE...NEW
IMPLEMENTED：逐条对应任务编号和源代码文件/方法
UNIMPLEMENTED：未完成/偏离设计/必须用户决策
BUILD：命令、环境、结果；不能编译写 BLOCKED
STATIC_CHECKS：Saveable/Harmony/权限/原资源操作对照
TESTS：逐项 PASS / FAIL / BLOCKED，证据路径/日志
RISKS：剩余风险及严重级别
ROLLBACK：上一可用 Commit 与回退指令
NEXT_PHASE_ALLOWED：YES / NO + 依据
```

**硬门槛**：涉及 SaveId 改动、授权放宽、重复金币/兵员、错误的读档恢复、Harmony 原版双执行、无说明地更改经济/军事配置或保护文件，一律 `NEXT_PHASE_ALLOWED=NO`。允许 Worker 在一个阶段内做多次小提交和中间自检，但不允许跨阶段带着 Fail 继续“赶进度”。

建议 Commit 前缀：

- `fix(army): close force transfer result and recovery lifecycle`
- `refactor(army): define campaign recovery ownership`
- `refactor(army): extract force task coordination`
- `refactor(army): separate supply execution services`
- `refactor(army): delegate fief accounting services`
- `refactor(army): separate garrison recruitment execution`
- `refactor(army): complete patch and dependency audit`
- `test(army): record integrated architecture acceptance`

## 6. 退出条件与回退

- 每阶段建立可独立审计的 Commit/分支；高风险 S1、S2、S4、S5 生成前后相同存档的名册/户数/粮食/金币快照。
