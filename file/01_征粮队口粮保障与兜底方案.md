# W1：征粮队口粮保障、出发校验与跨城兜底——修改设计和实现计划

**范围**：`ModifiedArmy` 驻军派出普通征粮队（`SupplyPartyMissionMode` 本地征粮）。跨城援粮独立分支只做回归与必要的保护检查。  
**基线**：`main@28f87c824ab07b4230e821052ae62e47e46ccf78`。  
**禁止行为**：直接给队伍 `ItemRoster` 凭空加食物；修改定居点民用 `Town.FoodStocks` 代替驻军粮仓；缺粮后仍无条件出发。

## A. 已确认代码与缺陷

### A1：已配粮，但仅有固定五天目标且不检查实发量

`SupplyPartyBehavior.TryCreateSupplyParty` 创建队伍、抽取驻军护卫、准备驮畜后调用 `TransferOutboundProvisions(garrison, supplyParty)` 再 `MoveToSettlement`。

```csharp
// 当前实现，便于定位，不能作为推荐的新算法
int provisionTarget = (int)Math.Ceiling(
    Math.Abs(supplyParty.FoodChange) * OutboundProvisionDays); // 5天
TransferFood(garrison.ItemRoster, supplyParty.ItemRoster, provisionTarget);
```

`TransferFood(...)` 会真实移动各食物物品，返回实际转移数，但调用点忽略返回值。**确认可发生**：粮仓为空或库存不足时，征粮队可能带着不足的口粮出发；到底有没有因此饿伤要由 W3 诊断。

### A2：出发失败和跨城援粮可用性判断未闭环

- `TryCreateSupplyParty` 的护卫抽取不足会恢复并冷却；粮食不足目前不是失败条件。
- `CanOrganizeLocalForaging(destination)` 当存在活跃本地任务或 `IsDispatchCoolingDown` 为真时，直接返回 true；这一方法被跨城援粮 `TryDispatchControlledAid` 用作否决条件。
- 建议将**“本地正在执行且确实能履约”**、**“冷却等待”**、**“本地可派且有可行口粮计划”**区分开；否则“口粮不足不派队”可能长期抑制跨城援粮。

### A3：游戏粮食模型

- 真正的军用粮仓是 `settlement.Town.GarrisonParty.ItemRoster`；`GarrisonLogisticsModel` 用它计算粮食天数。
- 原版镜像 `DefaultMobilePartyFoodConsumptionModel.DoesPartyConsumeFood` 对非驻军、非商队、非强盗等活动部队通常启用每日吃粮；**不要假设自定义征粮队不吃粮**。
- `FoodConsumptionBehavior` 还会维护饥饿状态、士气及其后续影响；不能直接把“伤兵变多”等同“饥饿导致伤兵”。

## B. 设计决策：粮食是真实库存，出发前先证明可行

### B1. 估算目标粮食

新增纯计算结构（非存档类型优先）`SupplyProvisionPlan`，推荐字段：`RouteDistance`、`TravelDaysToSource`、`EstimatedReturnDays`、`DailyFoodDemand`、`SafetyDays`、`RequiredFood`、`AvailableGranaryFood`、`PlannedLoad`、`CanDepart`、`Reason`。

计算过程：

1. `TryCreateSupplyParty` 在 `CreateSupplyParty`、初始化真实 escort roster 后获得 `supplyParty.FoodChange`。保证不在 `FoodChange` 初始化尚不准确时计算；零/异常值用可解释的 PartyFood 模型值或人数保守估算兜底，并 Debug 记录来源。
2. 用原版提供的地图行程距离与征粮队实际可用速度，估计 **去程** 和 **回程** 天数；行程距离单位和速度单位须核实，不能直接拿地图距离当“天”。多粮源任务要按每次目的地变更重新评估下一段。
3. 推荐要求 `requiredDays = max(OutboundProvisionDays, ceil(outboundDays + expectedReturnDays + safetyDays))`。`safetyDays` 建议初始值2天，但必须实测校正；如预计会在粮源采购口粮，须把“采购失败仍可安全返乡”的保护机制写清楚，不能将预计购入视为出发已持有。
4. `RequiredFood = ceil(max(0, -foodChange) * requiredDays)`，扣除征粮队已有可消费食物；食品一律通过 `TransferFood` 从驻军 `ItemRoster` 转移。
5. 不能一次将整个驻军粮仓倒空；必须评估当前驻军最小安全口粮要求和其它已承诺的运输需求。现有“最低保留”常量用于跨城援粮，应避免未经设计直接套用而永久阻断低粮驻军的征粮。记录保留策略和缺粮判断。

### B2. 出发前硬校验

修改 `TransferOutboundProvisions` 返回明确结果，不再为 `void`：

```csharp
// 方案级伪代码：类型和字段由 Worker 依现有项目定义
SupplyProvisionResult result = TryLoadOutboundProvisions(
    home, source.Settlement, garrison, supplyParty);
if (!result.CanDepart)
{
    RollbackSupplyDeparture(/* 当前已抽护卫、食物、驮畜和费用 */);
    LogExpectedProvisionShortage(result);
    SetDispatchCooldown(home, 1f);
    return false;
}
MoveToSettlement(supplyParty, source.Settlement);
```

`TryLoadOutboundProvisions` 必须比较 **需求食物、队伍现有食物、实际转移食物**。所需物品中断、实际搬运少于最低出发要求或容量不允许时应**原子化取消**并恢复护卫、驮畜、食品、可逆费用。上面的 `RollbackSupplyDeparture` 是设计级辅助方法名称（当前源码尚未存在），Worker 应从 `TryCreateSupplyParty` 已有的 catch 回滚逻辑提取共用函数，保证失败只回滚一次；库存不足属于**可预期业务拒绝**，不要通过抛异常后进入通用 `ModLogger.Error` 来处理，而记录一次 Info 或频率受控的 Warn。

注意：`TransferFood` 当前按食品数量而非食品负重约束。征粮队还有驮畜、粮食采购载重；要求 Worker 比对 `InventoryCapacity` / `TotalWeightCarried`，实际配粮不能让队伍超载。不要用“护卫出发口粮”吞掉所有后续采购空间。

### B3. 最终粮食分账

征粮队物品栏是食物混合存储；以任务的 `RequestedFood` 表示待采购送回数量，切勿把护卫口粮直接计入“采购成果”。确保：

- `RecordSourceVisit` 只扣除 `AcquireFoodAtSource().FoodAcquired`；
- `CompleteMission` 归还队伍**剩余真实食物**到驻军，不把已消耗粮食“退回”；
- 发生多次采购时，前一站购得食物有可能被护卫吃掉，这是实际损耗，最终到货量必须按真实库存及任务记录核算，避免在日志中以“总采购量”冒充实际归还量；
- 跨城援粮 `TryDispatchControlledAid` 当前已经校验 `loaded < cargo + returnFood` 时失败；不要无意删除其校验，对长途跨城援粮同样评估五日返程口粮是否足够。

## C. 任务途中缺粮保护

1. 在 `OnHourlyPartyTick` 只做**轻量判定**，不要每小时完整重算不可缓存的多路线模型；每次更换粮源或日更时重算剩余行程和可用粮食天数。
2. 若 `IsStarving` 或剩余食物不足以安全到达目前目标，分级处理：已接近安全粮源则继续但报警；存在更近可合法采购粮食的粮源则重新评估；确实无法安全完成则标记任务中止、选择合理的返航/友方补给方案。禁止凭空生成粮食或随意跨地图跳回家。
3. 中途任务中止应有稳定的冷却，防止每日无限创建、无限失败；必须保证人员、牲畜、钱、食物回归或按实际损失结算。
4. 对多来源 `ChangeSource` 的任务，扣除本次采购后根据实际食物和预估路程评估下一站；不应为了凑齐 `RequestedFood` 而让护卫饿死。

## D. 与跨城援粮的兜底衔接（必修）

现有 `CanOrganizeLocalForaging()` 把冷却等同可以组织征粮，可能会拦截 `TryDispatchControlledAid`。

请拆出无副作用判断，例如：

- `HasActiveLocalForagingMission(home)`：是否已有真正有效的本地征粮任务；
- `CanActuallyDispatchLocalForaging(home, status)`：是否有护卫、合法粮源、运输容量、可行起程口粮（只读估算），不能将“处于冷却”当作可行；
- `IsDispatchCoolingDown` 仅控制频率，不能宣称本地能够提供粮食。

跨城援粮是否应跳过活跃任务取决于已有 `GetRemainingAidNeed` 和未入库补给计数，必须保留不重复补给保护。建议至少满足：**本地因粮不足被拒绝时，如果跨城援粮客观可行，不因该拒绝冷却而继续拦截跨城援粮**。若“本地在执行但快断粮”也需要跨城援助，应依实情修订。不要制造任务重复或粮食重复结算。

## E. 需要修改的具体文件

## F. 测试矩阵（必须记录粮食守恒）

- [ ] 粮仓充足、粮源近：出发有实际口粮、无粮食凭空增加、返回物品正确。
- [ ] 粮源很远（大于五天往返）：口粮覆盖路线及安全余量，长途不因固定五天耗尽。
- [ ] 粮仓0/不足：不能带着0粮出发；护卫、驮畜、花费、金币完整回滚；不重复派遣。
- [ ] 家乡粮仓不足、本地不能出发但友城有粮：跨城援粮能够进入可行性判断并正常派遣。
- [ ] 护卫数不足50：现有拒绝及恢复流程不退化。
- [ ] 途中换粮源、多站采购：继续航程前重新评估口粮，最终到货不重复统计。
- [ ] 负重逼近上限：不超载，保证粮食和驮畜不造成无法采购。
- [ ] 源定居点失效、遭围城、敌对：安全返航/改道，无无效连锁任务。
- [ ] 途中读档：任务/粮食/派遣冷却持续一致，不重复配送。
- [ ] 多支运输队同时竞争同一食品来源：不会重复消耗同一批库存。
