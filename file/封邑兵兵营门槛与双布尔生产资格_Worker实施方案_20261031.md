## 一、已核对的当前实现

### 1.1 封邑兵门槛只差配置传递

- `ModifiedArmy/ModifiedArmy/Fief/Models/PartyData/FiefPartyReinforcement.cs` 的 `WithdrawFiefTroopEntries(int maximumCount)` 已读取 `SettlementManpowerProductionBehavior.GetBarracksLevel(_settlement)`，并筛选 `entry.Weight > 0 && entry.RequiredBarracksLevel <= barracksLevel`。**不要重写抽样与入库逻辑。**
- `ModifiedArmy/ModifiedArmy/Fief/Models/FiefPartyTemplate.cs` 的 `ParseTroop()` 当前仅使用 `new TroopProductionEntry(troop, troopWeight)`；未解析 XML 的 `barracksLevel`，第三参数因此默认 0。
- `ModifiedArmy/ModifiedArmy/Recruitment/Pools/Models/TroopProductionTemplate.cs` 的 `TroopProductionEntry` 构造器已经接受 `int requiredBarracksLevel = 0`，并公开只读 `RequiredBarracksLevel`。
- `ProfessionalTroopTemplate.ParseTroop()` 已通过 `TroopProductionTemplateUtility.ReadOptionalInt(troopNode, "barracksLevel", 0)` 解析同名属性，可直接复用实现风格。
- `SettlementManpowerProductionBehavior.EnsureDailyProduction()` 先计算 `fiefCount`，再调用 `fiefData.ProduceDailyFiefTroops(fiefCount)`；生成士兵直接进入封邑名册，不经过驻军。未成功生产的数量会回补 `FiefProductionProgress`（见第六节风险）。

### 1.2 当前 `TroopProductionKind` 的真实用途

```csharp
[Flags]
public enum TroopProductionKind
{
    None = 0,
    Professional = 1,
    Fief = 2
}
```

该枚举目前用于选择**生产路径/模板/进度账本**，例如 `TroopProductionTemplateRepository.Resolve(settlement, kind)`、`SettlementManpowerProductionBehavior.GetDailyProduction(settlement, kind)`；**不是每个 `CharacterObject` 实例的永久身份标签**。

跨模块约束：`ModifiedPolitics/ModifiedPolitics/HeroOffices/Patches/MilitaryOfficeRecruitmentPatches.cs` 的 Harmony Postfix 直接使用参数 `TroopProductionKind kind`；不能随意删改 `GetDailyProduction` 的方法签名。

### 1.3 同一兵种可以拥有双生产资格

帝国港口模板 `empire_town_port` 中，`NPCCharacter.empire_marine_t3` 同时出现在 `fiefPartyTemplates.xml` 和 `professionalTroopTemplates.xml`。这属于合法配置，目标行为是：

```text
IsFief = true
IsProfessional = true
```

但这仅表明**该兵种可以来自两条生产渠道**，绝不意味着名册中的某一名士兵同时属于两套服役系统。实际服役身份仍以封邑来源、在役批次与真实名册判定。

## 二、需求 A：封邑兵生成按兵营等级检查

### A1. 用户明确规则

1. **巴旦尼亚（Battania）和诺德（Nord）的高级兵**：直接生成不要求兵营等级（`barracksLevel=0`）。
2. **其他文化的高级兵**：直接生成必须有对应兵营等级（`barracksLevel > 0`），不能在 0 级兵营免费直接生产高级精锐。
3. 此规则同时检查封邑生产模板、职业兵生产模板中相应的高级**直接生产根兵种**；不可只改封邑 XML 而忽略库赛特等已经走职业兵渠道的精锐。
4. `barracksLevel` 仅限制**新兵直接生产资格**。已有库存、征召/招募已存在士兵、战斗升级、返乡与保存记录不得因此自动销毁或降级。
5. **生产速度与生产资格不同**：巴旦尼亚、诺德允许 0 级兵营生产高级兵，不代表兵营对职业兵训练速度的加成必须取消。现有共享兵源、权重、容量和军事制度仍生效。
6. 不新增“封建兵营”、兵种池或另一份士兵库存；封邑新兵依旧直接进入现有封邑名册。

### A2. 规则落点与具体修改

**必须修改文件 A：** `ModifiedArmy/ModifiedArmy/Fief/Models/FiefPartyTemplate.cs`

在 `ParseTroop()` 成功解析合法 `troop` 与 `troopWeight` 后，读取同名属性，并传入现有构造器：

```csharp
int barracksLevel = TroopProductionTemplateUtility.ReadOptionalInt(
    troopNode,
    "barracksLevel",
    0);

_troopEntries.Add(new TroopProductionEntry(
    troop,
    troopWeight,
    barracksLevel));
```

- 属性缺省必须为 `0`，保证旧 XML 兼容。
- 不修改 `TroopProductionEntry` 的字段类型和序列化格式（该条目本身为模板只读数据）。
- 不额外增加“高阶兵种自动忽略配置”的硬编码分支；各文化门槛统一由现有 XML 管理。
- 不修改 `WithdrawFiefTroopEntries()` 已存在的兵营筛选，除非发现针对该功能的真实缺陷并单独报告。

**必须修改文件 B：** `ModifiedArmy/ModifiedArmy/ModuleData/fiefPartyTemplates.xml`

- 遍历所有 `town_port`、`town`、`castle` 三种模板，而非只改城镇。
- 为帝国、瓦兰迪亚、阿塞莱、斯特吉亚、库赛特的**高级直接生产根兵种**明确加上正数 `barracksLevel`。普通低阶兵种无需因本需求统一加门槛。
- 巴旦尼亚、诺德高级根兵种明确 `barracksLevel="0"` 或保持省略（省略即 0）；为了审查可读性，建议高级兵显式写出 `0`。
- 保持所有 `id`、`weight`、条目数量、升级树、产量公式与 AI 征召权重不变。
- 验证每个 XML 根兵种均在实际 `CharacterObject` 和对应 `basic_troop_config.xml` 中可解析；无效的兵种 ID 是配置缺陷，不应被算法自动替换为别的兵种。

**必须检查/按需修改文件 C：** `ModifiedArmy/ModifiedArmy/ModuleData/professionalTroopTemplates.xml`

- 检查所有文化的高级直接生产根兵种。巴旦尼亚、诺德高级根兵种应为 `barracksLevel="0"`；其他文化高阶根兵种应为正数。
- 当前库赛特 `khuzait_torguud` 省略 `barracksLevel`（即 0），与新规则冲突，需要明确设置非 0 门槛。
- 当前斯特吉亚 `druzhinnik`、帝国 `imperial_cataphract`、阿塞莱 `aserai_mameluke_regular` 已设置 3，优先保留，不要为了形式统一而降低其既有门槛。
- 对巴旦尼亚、诺德现有职业兵模板中的直接生产高级兵，如当前门槛大于 0，需要依用户文化例外调整为 0；非高级兵是否保留现有门槛，不在本任务强制变更范围。
- 现有职业兵模板解析逻辑已支持 `barracksLevel`，无需改写 `ProfessionalTroopTemplate.cs`。

| --- | --- | ---: | --- |
| `vlandian_knight` | 封邑 | 2 | T4 骑士，原为 0 |
| `khuzait_torguud` | 职业 | 2 | T4，可汗亲卫路线起点，原为 0 |

### A3. 配置示例

```xml
<!-- 瓦兰迪亚封邑：骑士需要 2 级兵营；普通步兵仍无直接生产门槛 -->
<troop id="NPCCharacter.vlandian_knight" weight="1" barracksLevel="2" />
<troop id="NPCCharacter.vlandian_footman" weight="3" />

<!-- 巴旦尼亚封邑：英雄无兵营门槛 -->
<troop id="NPCCharacter.battanian_hero" weight="1" barracksLevel="0" />
```

**边界语义**：当实际兵营等级小于配置要求时，该根兵种不参加本次封邑新兵随机抽取；同一模板的其他合格根兵种继续按原权重随机生产。旧有该兵种仍可出现在封邑名册并被征召。

## 三、需求 B：兵种生产资格使用两个布尔标志

### B1. 用户明确规则与禁止做法

兵种可通过哪种渠道生产，只表达为两个独立布尔值：

| `IsFief` | `IsProfessional` | 含义 |
| --- | --- | --- |
| `false` | `false` | 当前封邑、职业模板都不认可此兵种 |
| `true` | `false` | 仅有封邑生产资格 |
| `false` | `true` | 仅有职业生产资格 |
| `true` | `true` | 两种生产渠道都认可 |

**不使用** `type = 1 / 2 / 3`、`Fief | Professional` 或相加值来代表某兵种的双渠道身份。也不对 `CharacterObject` 添加全局唯一的“封邑/职业”分类整数。

### B2. 数据权威：从已有模板计算布尔值，不保存重复状态

建议设计一个**只读值对象或等价结果**，名称可根据仓库规范调整：

```csharp
public readonly struct TroopProductionEligibility
{
    public bool IsFief { get; }
    public bool IsProfessional { get; }

    public TroopProductionEligibility(bool isFief, bool isProfessional)
    {
        IsFief = isFief;
        IsProfessional = isProfessional;
    }
}
```

建议通过 `TroopProductionTemplateRepository` 或已有同域只读查询模型提供：

```csharp
TroopProductionEligibility GetEligibility(
    Settlement settlement,
    CharacterObject troop);
```

**语义必须明确：**

- 结果基于**指定定居点**的文化与 `town` / `town_port` / `castle` 模板解析，不能因为“某文化任何一个城镇曾定义此兵种”就让全地图固定为 `true`。
- `IsFief`：当前封邑模板是否认可该兵种；沿用 `FiefPartyTemplate.IsEnableTroop(troop)` 的根兵种与合法升级树判定。
- `IsProfessional`：当前职业模板的根兵种或其合法升级树是否包含该兵种；如要扩展到升级树，请实现带 `visited` 的**只读**遍历，不在查询时修改模板、名册或游戏状态。
- 这里的 bool 是**结构性生产来源资格**，不是“今天还能否生产”。兵营不足、`weight=0`、共享兵源不足、财政不足、库存已满等运行时约束需由原有生产/审批逻辑判断。必要时单独命名 `CanProduceNow`，不得把布尔来源标志当成即时生产许可。
- `troop == null`、`settlement == null` 或模板不存在时返回 `false / false`，不可默认单向职业或封邑身份。
- 不在存档中保存这两个字段；不将其放入全局可变 `Dictionary<CharacterObject,...>` 作为第二权威台账。查询量不大则直接算；如必须缓存，需基于定居点和当前模板、正确处理 Campaign 生命周期及重新加载。
- 已经转入领主队伍或驻军的一名士兵，是否为在役封邑兵，仍由 `FiefServiceBatch` 与实际名册、批次转移和对账确定。**禁止用 `IsFief == true` 给所有同类职业兵自动免薪，或把驻军同 ID 士兵都视为封邑在役兵。**

### B3. 枚举兼容：拆分“流程选择器”和“布尔资格”

现有 `TroopProductionKind` 不是兵种标签，而是函数参数和模板类型选择器。为避免引入大规模跨模块变化，本任务建议：

1. **对兵种资格的新增 API 只暴露 `IsFief` 与 `IsProfessional` 两个 bool；不得引入组合整数值。**
2. 现有 `TroopProductionKind` **保留为旧生产流程的单选路由枚举**（`Professional` 或 `Fief`），不用于表示“某兵种同时属于两类”。现有枚举数值及 `GetDailyProduction(Settlement, TroopProductionKind)` 方法签名不变，确保 `ModifiedPolitics` Harmony Postfix 兼容。
3. Worker 全仓检索是否存在任何 `TroopProductionKind` 位或操作。若确认没有组合用法，可删除该枚举上误导性的 `[Flags]` 属性及“Flags allow…”注释，将其明确记为**单选路由**；但不要改变枚举类型、成员名称、数值和现有 API 参数。若存在组合使用，先提出兼容迁移方案，不能强行删改。
4. 不把 `ITroopProductionTemplate.ProductionKind` 直接替换为两个 bool；单个模板本身是某一生产渠道，双 bool 表示的对象是**兵种在当前定居点的生产资格**。两个概念必须分离。
5. 不新增诸如 `Both=3` 或 `Professional | Fief` 的实体类别。

### B4. 典型验证场景

- `empire_town_port` 的 `empire_marine_t3`：`true / true`。
- 某定居点只在封邑模板声明的兵种：`true / false`。
- 某定居点只在职业模板声明的兵种：`false / true`。
- 未在两套模板出现也不属于任何合法升级树的兵种：`false / false`。
- 在另一文化或另一类型定居点查询同一兵种时重新解析，不能复用前一种场景的结果。
- 兵营等级从 0 升到 3，`IsFief / IsProfessional` **来源资格不应因设施改变**；实际 `WithdrawFiefTroopEntries` / 职业兵候选资格应正常变化。

## 六、需主动报告、不得擅自扩大的风险

1. **封邑生产进度积压**：当前 `EnsureDailyProduction()` 在 `produced < fiefCount` 时把未产出的数量重新写回 `FiefProductionProgress`。如果某封邑所有兵种都被兵营门槛挡住，进度可能不断积累，并在升级兵营后形成异常突发产出。此现象在当前代码结构中真实可能发生。Worker 必须测试并报告；**本任务默认不调整生产经济公式**。如需处理，应提出独立的小范围修复及预期数值后再执行，不要悄悄丢弃进度。
2. **高级定义**：本方案按实际 `CharacterObject.Tier >= 4` 进行审计，具体门槛不凭 XML 兵种名称猜测。T4 建议 2、T5+ 建议 3 是默认平衡建议，而非额外增加“动态按 Tier 自动禁止”的运行时代码。
3. **升级树与职业模板**：根兵种直接生产条件与已经存在的后代兵种资格是不同问题。双 bool 对升级树的判定不能绕开原生产的 `RequiredBarracksLevel` 条件。
4. **兵种定义 ID 失效**：解析缺失时只能明确报错/记录原因，不可偷偷回退到其他兵种或创建第二份映射。
5. **不相关功能**：不要修改 AI `MinimumFiefRecruitBatch=25`、权重征召分配、驻军调拨、在役免薪期、军费预算、军事制度、独立势力任务、存档模型或完整兵种树。
6. **兼容性**：若跨模块 Harmony 签名、缓存生命周期或游戏 API 与本方案示例冲突，以最新实码为准；禁止以“清理枚举”为由大范围重写。
