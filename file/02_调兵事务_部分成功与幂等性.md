# W2：统一调兵执行语义、部分成功与幂等性

## 发现：真实转移和布尔执行状态目前可能不一致

现有 `PartyExchangeService` 已有良好的前置快照校验、实际名册对账、反向补偿操作，必须保留。不过 `ExecuteFiefMobilization` 在批准 N、人实际征召 M 人 (`0 < M < N`) 时，返回 `Result(false,"AuthoritativeFiefResultChanged", M)`。`ExecuteFiefReturn` 同样存在返回“失败 + 已归还人数”的情况。`AiForcePlanningBehavior.ExecuteAtSettlement` 会增加 `task.Progress`，却只根据 `result.Executed` 决定 `Completed/Cancelled`。`PartyExchangeService` 只有 `result.Executed == true` 才将 `OperationId` 写入 `_completedOperationIds`。

因此存在**部分实际生效但业务上标记失败**的风险；是否复现重放要做实机验证，不可当成已经证实的复制兵漏洞。

## 设计目标

1. **真实状态唯一**：操作结果报告实际提交的数量，且有显式终态。
2. **计划纯计算，提交有边界**：`PartyExchangeModel.BuildPlan` 无修改；`PartyExchangeService` 执行前重新校验来源、归属、名册指纹、容量和封邑在役批次。
3. **幂等清晰**：同一操作即使部分成功也不允许用同一个 `OperationId` 再次盲目提交；未完成需求应根据最新权威状态生成新审批与尝试编号。
4. **回滚诚实**：回滚失败必须标为待恢复，不能伪装成“未执行”。

## 建议契约（只作参考，不必照搬命名）

```csharp
public enum TransferCommitStatus
{
    Rejected,             // 资源未变化
    Committed,            // 完全提交
    PartiallyCommitted,   // 已提交一部分
    RolledBack,           // 改动完全回滚
    RecoveryRequired      // 非法中间态/回滚不能确认
}

public sealed class TransferExecutionResult
{
    public TransferCommitStatus Status { get; init; }
    public string ReasonCode { get; init; }
    public int RequestedCount { get; init; }
    public int ApprovedCount { get; init; }
    public int ActualCount { get; init; }
    public string OperationId { get; init; }
}
```

项目目标为 `netstandard2.0`；如使用 `init`，注意已引用 `IsExternalInit`，也可用现有 `set` 风格降低迁移成本。

## 修改步骤

1. **先加适配层**：在 `PartyExchangeExecutionResult` 增加等价状态字段；先保持 `Executed` 兼容属性，其语义要明确为“完全成功”，但所有调用处逐个迁移到 `Status` 判定。
2. **普通名册转移**：沿用 `ExecuteRosterTransfer` 当前反向补偿和守恒校验，捕获补偿中的异常，校验补偿后两侧人数、伤员/受保护数；无法恢复标 `RecoveryRequired` 并输出 Error。不得静默 `catch { }` 后认定恢复成功。
3. **封邑动员**：调用权威 `FiefPartyManager.RecruitFiefTroopsFromSettlement`，核对实际人数及在役批次；结果 0、部分、完整分别有对应状态。不要为了凑满批准人数而额外征召。
4. **封邑返乡**：以 `TryReturnFiefTroops` 实际返回量为准，核对同源批次/在役台账；同样明确部分成功。
5. **任务协调**：`AiForcePlanningBehavior.ExecuteAtSettlement` 不再使用简单二分状态；部分成功需要记录已提交量，重新采集权威来源与缺口，结束本次 attempt，按业务规则重新规划；异常待恢复停止自动重复转移。
6. **幂等**：`_completedOperationIds` 改为“已有实际提交的操作 ID”，不局限于完整成功；对任务级别附持久化进度或明确可恢复身份。需要评估存档读取过程并处理重启/加载后的重复执行。
7. **通用资源操作**：将实际资源转移的底层守恒与补偿抽到 `Infrastructure/Transactions/`，不要把驻军、封邑、征粮的业务限额规则移动到基础设施层。

## 接口兼容与回归

- 不改变 `PartyExchangeOperation`、`Purpose`、已有 Saveable 字段编号，除非独立迁移。
- 继续使用 `PartyTransferOwnershipPolicy.IsAuthorizedRosterPair`，保留真实驻军身份、同 Clan、占领后单向捐兵例外等限制。
- `TroopTransferService` 和 `ReinforcementTransferService` 先纳入调用图，分步收敛重复操作；禁止在一个 PR 中同时改动所有转移算法。

## 测试矩阵

| 情形 | 期望 |
|---|---|
| 申请30，实际转30 | Committed；只生效一次 |
| 申请30，实际转20 | PartiallyCommitted；任务累计20，并停止重复原尝试 |
| 申请30，实际转0 | Rejected/相应无提交状态；不写已提交集合 |
| 执行前名册改变 | Rejected；双方名册不变 |
| 补偿成功 | RolledBack；双侧兵种/伤兵/数量守恒 |
| 补偿失败 | RecoveryRequired；不继续自动重试；输出 Error |
| 同一 ID 重复调用 | 已提交时不会二次变化 |
| 存档恢复后重复进入定居点 | 原操作不被重复提交，允许新审批合法继续 |
| 敌军围城、Clan 不匹配、非真实驻军 | 均禁止转移，结果清晰 |

## 禁止事项

- 不直接给兵员清零或重新造兵作为“回滚”。
- 不在异常中默默丢弃异常后声称人数守恒。
- 不因为 `ActualClan` 偶尔为空就扩大授权；真实驻军归属的修复政策必须保留。
- 不在补偿失败时返回 `Executed=false,TransferredCount=0` 而隐藏真实副作用。
