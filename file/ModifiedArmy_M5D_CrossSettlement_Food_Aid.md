**本阶段交付物：** 保持旧本地征粮功能，给现有征粮队增加同Clan的跨城送粮模式；护卫从来源驻军出发，送粮后返回原驻军。

## 共同约束（各阶段必须遵守）

- **同 Clan 限定：** 首版军事增援和跨城援粮仅允许同一 Clan 的来源及目标，不因同 Kingdom 放宽；创建、装载、交付和异常回收都复核归属。
- **资源真实：** 转移真实 `MemberRoster` / `ItemRoster`；不生成虚拟兵粮，不保存 CargoManifest；战损、耗粮后只按实际余量交付。
- **任务分离：** 军事增援队单程，幸存士兵到站归并目标驻军；援粮征粮队往返，护卫返回来源驻军；现有本地自用征粮保持不变。
- **普通领主不承运：** 不修改常规 `PartyForceTargetModel`、`AiRecruitmentBehavior` 或原生 Army 模型；删除旧第五阶段新增 Army Harmony 补丁，但不得删除全局 `PatchAll`。
- **异常安全：** 交付/回收前复核合法 Clan 和驻军接收容量；已存活兵员或有归属价值的物资不能被直接销毁；读档、重复事件不得造成二次装卸。
- **开关：** 在 M5-E 实机验收前保持自动派遣关闭，之前仅允许受控入口。

## D1. 跨城援粮何时触发（原方案原文）

### 1.2 自行征粮优先，跨城援粮兜底

首先用现有 `GarrisonLogisticsModel` 和 `SupplyPartyBehavior` 判断目标确实存在粮食缺口、本地库存/生产/采购不能解决，以及是否能够正常组织本地征粮。**可以正常自行征粮的目标不额外申请跨城援粮**。

无法自行征粮时：

- **目标还缺兵**：优先由军事增援队附带外部可调拨粮食，减少地图Party数；若不能提供足够额外粮食，不阻塞必要的兵员增援，剩余粮食缺口可由独立援粮处理。
- **目标当前不需要增兵（或临时没有合法兵源）**：允许其他同 Clan 驻军派征粮队送粮、交付后返程。不能为了运粮强行给目标驻军添加士兵。
- 援粮请求由**目标剩余净缺口**决定，扣除已派运输队真实携带/已承诺的预计交付粮食；只批准可由源地实际库存支付的数量。

“能自己征粮”必须使用有效条件，不可简单用 `驻军人数 >= 50` 代替；当前现有征粮队还需要未围城、护卫健康可抽调、有来源、冷却等校验。对于暂时冷却、危险区域等状态如何救援，第一版采取保守的“不贸然强派”策略并记录原因日志。

## D2. 援粮状态机（原方案原文）

### 3.2 跨城援粮征粮队（正常往返）

```text
目标缺粮且不能自行征粮
   → 从同Clan其他来源驻军抽50名真实健康护卫，保留返程编制
   → 从来源可安全调拨的现有粮食装载援粮 + 往返口粮
   → DeliveringAid
   → 目标合法、缺粮 → 卸载实际可交付援粮（保留返程口粮）
   → ReturningFromAid
   → 来源合法且有返程驻军预留 → 护卫/剩余物资归队
   → Completed → DestroyPartyAction

目标失效 → 停止卸粮 → ReturningFromAid
来源失效 → Recovering → 同Clan其他安全驻军接收护卫/物资
途中全军覆没 → Destroyed（真实损失；释放来源编制预留、冷却）
```

新增模式不得影响现有 `TravelingToSource → ReturningHome → Completed` 自用征粮状态机。跨城援粮第一版**直接由来源驻军已有安全余粮发运**，不走原征粮队多站采购路径；其目的就是让本地缺粮的目标得到其他Clan内部据点援粮（实际限定同Clan）。

## D3. 保持旧档兼容地扩展SupplyPartyComponent（原方案原文）

### 4.2 扩展现有 `SupplyPartyComponent`（兼容旧存档）

该类现有 `[SaveableRootClass(1)]` 和 `[SaveableProperty(1..5)]` 必须原封不动。建议**只向后追加**：

| Property ID建议 | 字段 | 用途与兼容默认 |
|---|---|---|
| 6 | `int MissionModeValue` | 0=原自用征粮，1=同Clan援粮；旧存档默认0 |
| 7 | `Settlement AidDestination` | 仅援粮模式使用；旧存档默认null |
| 8 | `Clan DispatchClan` | 新援粮模式创建时锁定派遣Clan；旧模式null不改变原有归属行为 |
| 9（建议） | `Settlement RecoverySettlement` | 源失守后异地回收，旧档null |

不要修改既有 `SupplyPartyMissionState` 的0/1/2整数值。追加 `DeliveringAid`、`ReturningFromAid`、`Recovering` 等状态值即可，`SupplyPartyBehavior` 先按 `MissionModeValue` 分派不同的任务推进规则。

对于援粮任务的临时Party，归属应基于持久化 `DispatchClan`，不能调用原 `SynchronizeOwnership()` 把部队归属转给新占领源地的Clan。原自用征粮仍沿用原有逻辑，除非另开修复任务。

## D4. 粮食、护卫与经济规则（原方案原文）

### 6.2 兵力容量和征粮队返程预留

- 军事增援队从源地转走兵员后**不会返回原驻军**，因此不得像征粮护卫一样给来源驻军虚假的回程编制预留。源地有效人数自然下降。
- 自用征粮队/跨城援粮队的护卫应持续占用**实际预期返程驻军**的编制。`GarrisonRecruitmentCapacity.GetActiveSupplyEscortCount` 必须兼容新援粮状态与异常改道；不能在其出发后让来源驻军自动补员占满返程席位。
- 到达与回程时以 `GetHardFreeSlots`/`GetTransferFreeSlots` 等真实容量批准为准；若实际容量改变，暂停超额归并并执行安全回收或记录待回收，而不是突破硬上限。
- `GetActiveSupplyEscortCount` 应识别归属失效的源地，不得把原Clan护卫计入被敌对Clan占领的驻军有效编制。

### 6.3 粮食与经济处理

- 要分清临时队自身沿途消耗口粮和真正计划交付的粮食；纯援粮队还要保留**回程口粮**。
- 来源城堡驻军仓库食物可按模型判定的安全余粮真实调出；城镇市场的粮食需要真实购买与支付，不可将市场物品无偿视作Clan库存。
- 抽调士兵、征粮护卫外出和归队应核对现有军饷统计，不使同一士兵在临时Party及原驻军重复结算工资。
- 驮畜、骑乘马与普通物资在完成、回收、失败时都必须有实际 `ItemRoster` 去向，不得凭空复制或丢弃。

**实施顺序：** 确定目标确实无法自行征粮 → 同Clan源驻军可安全抽调50名护卫及余粮 → 真正扣源地Roster/ItemRoster并创建队伍 → 到目标只交粮食（保留返程口粮与护卫） → 返回来源将护卫和剩余物资归队 → 若源地已失效，找同Clan替代安全接收点。原有多站采购模式不作功能改变。

**注意：** 原有自用征粮的旧存档 `MissionModeValue=0` 应保持兼容；新跨城援粮不能因源地易主将Party归属变更为占领者；同Clan限制应用于全过程而非创建时一次检查。

## D6. 验收清单（源方案第8.1节选）

- 仅同 Kingdom 非同 Clan：**不得**派遣军事增援队或跨城援粮队；玩家Clan与AI Clan等同执行。
- 纯粮食需求且本地已可正常征粮：优先本地征粮，不派援粮；本地不可自行征粮：由同Clan另一驻军派50护卫援粮队。
- 援粮队送粮到站：交付不包含护卫与必要返程口粮，随后原路/安全路线回源归队；来源驻军自动补员不能占用护卫保留编制。
- 援粮队途中来源易主：Party保持派遣Clan归属，转向同Clan替代回收驻军；敌方新驻军不为其预留编制。
- 不同来源并发援粮：实际库存减少、在途贡献扣抵目标缺口，不得重复采购或无偿取走市场库存。
- 原有自用征粮队的状态0/1/2旧存档继续可读，原有多站采购功能仍正常，新的Mode默认值不误判旧任务。
- 保存发生在创建后、临时Party已抵达、交付中、回收途中：读档恢复后无重复派兵/卸粮/销毁；多次事件调用幂等。
- 敌军能追击并进入战斗，临时运输队会规避强敌；威胁解除能回到任务目标，不因小时Tick覆盖逃跑而反复送死。
- 任务创建失败：源地兵员、粮食、马、资金有明确回滚或保留记录；不遗留幽灵Party。
- 工资、负重、速度、封邑兵归属、原驻军与征粮队的硬容量在批量运行20～30个战役日后无系统性漂移。

**放行标准：** 援粮往返真实结算、护卫返程预留正确、不超编；既有本地征粮流程和旧档不退化，援粮不为目标虚增兵员。
