# 2026-10-23 统一调兵崩溃异常分析报告

## 1. 结论

本次崩溃由 `ModifiedArmy` 的封邑动员计划触发，与 `ModifiedPolitics` 的总督调整无直接关系。

统一调兵在为一支 AI 领主部队生成 `Fief -> MobileParty` 调动清单时，审批结果包含 `imperial_menavliaton`，但同一次计划使用的封邑来源名册不包含该兵种。`PartyExchangeModel.AddAmount()` 未检查查找结果是否为空，随后读取空对象的 `WoundedNumber`，产生 `System.NullReferenceException` 并终止游戏。

## 4. 直接原因

原代码按 `CharacterObject` 在来源名册中查找条目：

```csharp
TroopRosterElement element = roster.GetTroopRoster()
    .FirstOrDefault(item => item.Character == troop);
int healthy = Math.Max(0, element.Number - element.WoundedNumber);
```

本次 `FirstOrDefault()` 没有找到 `imperial_menavliaton`，所以 `element == null`。`WoundedNumber` 成员本身存在，异常来自对空 `element` 的成员访问。

## 5. 根因

封邑征召预览使用了残留的全局分类判断：

```csharp
SoldierTypeClassifier.IsFiefTroop(troop)
```

该函数实际判断兵种是否被全局归类为 `Militia / Sergeant / Marine / Slave / Retinue`。它不是“是否属于当前封邑模板”的判断。

`imperial_menavliaton` 在 `basic_troop_config.xml` 中被归入 `SergeantTroops`，因此全局判断返回 `true`；但帝国城堡的 `FiefPartyTemplate` 并未启用该兵种，因此 `GetFiefTroopRoster()` 将其排除。最终形成两个不一致的集合：

```text
征召审批集合：包含 imperial_menavliaton
实际封邑来源名册：不包含 imperial_menavliaton
```

这属于旧分类接口残留在封邑征召路径中，不是 `TroopRosterElement.WoundedNumber` API 缺失，也不是总督调整造成的数据损坏。

## 6. 修复内容

### 6.1 统一封邑兵资格

封邑招募的预览、常规招募和选择提交统一改为：

```csharp
_fiefPartyTemplate.IsEnableTroop(troop)
```

审批集合和实际来源名册因此使用同一封邑模板，不再把普通职业兵误当作当前封邑可动员兵。

### 6.2 交易边界防御

`PartyExchangeModel.AddAmount()` 增加以下复核：

- `manifest`、`troop`、`roster` 和数量必须有效；
- 兵种必须真实存在于本次来源名册；
- 调动数量不得超过来源条目当前数量；
- 不满足条件时拒绝该清单项并记录错误日志，不再触发空引用；代码只引用英文资源键，中文内容集中维护在 `submodule_strings.xml`。

### 6.3 第六阶段异常隔离

- 每支 AI Party 的每日规划独立捕获异常；单支异常不再终止整个每日 Tick。
- 每次定居点访问的统一交易独立捕获异常；失败交易留到后续重新规划。
- 读档任务逐项重验证；单条旧任务损坏时只取消该任务。
- 完成、取消、失活及长期未验证的任务会被清理。
- `modifiedarmy_party_garrison_exchange_days` 保留原存档键，同时清理超过保留期的历史访问记录。
