# 封建兵服役机制当前实现

本文记录 `ModifiedArmy` 当前已经落地的封建兵征召、服役、免薪、对账和返乡实现。旧设计稿中的存档迁移方案已废弃，以本文和实际代码为准。

## 1. 数据断代

- 旧 `FiefTroopDetachment` 仅保留在 SaveDefiner 中，用于让历史存档能够完成反序列化。
- 旧存档的 `RecruitedTroopDetachmentList` 与 `ReturnedTroopDetachmentList` 在封邑数据初始化时清空。
- 不猜测旧记录属于哪个 Party，不迁移旧免薪期，也不再输出 `Legacy batch ... has no provable serving party`。
- 旧记录不参与封建兵人数、工资减免、Hearth 占用、返乡或战损结算。
- 从本版本发生的新征召开始，全部使用下述新结构重新记录。

## 2. 新数据结构

### `FiefServiceBatch`

每次成功征召都会建立独立的在役批次，保存：

- 实际征召兵种及人数；
- 目标 `MobileParty.StringId`；
- 已服役天数；
- 来源文化决定的免薪天数快照；
- 上次更新时间；
- 稳定的批次 ID。

运行期通过 Party ID 恢复 `MobileParty` 引用。来源封邑不在批次中重复保存，由持有该批次的 `FiefPartyData` 决定。

### `FiefReturnBatch`

返乡士兵使用独立冷却批次，只保存：

- 兵种及人数；
- 剩余冷却周数。

它不包含 Party、服役时间和免薪信息，避免在役数据与冷却数据再次混用。

## 3. 征召与兵源占用

- AI 自动征召和玩家手动选择都按“实际成功转移”的名册建立批次。
- 每次征召单独建立批次，不按来源封邑或剩余时间合并。
- 手动选择会重新核验封邑可用人数、目标 Party 容量和实际批准人数，避免原始选择名册造成虚增。
- 新批次注册到 `FiefPartyManager` 的运行期 `Party -> 批次` 索引。
- 征召时继续占用当前封邑兵源对应的 Hearth；战损只释放占用，不恢复 Hearth，真实返乡才恢复 Hearth。

## 4. 服役与工资

- 在役批次不再因 `MaxServiceWeeks` 到期而消失。
- 服役天数按战役日幂等推进，同一天重复调用不会重复增加。
- `ServiceDays < FreeWageDays` 时，该批次登记的具体兵种免薪；达到免薪期限后继续服役并正常计薪。
- 文化免薪天数由 `ModuleData/modConfigs.xml` 的 `FiefFreeWageDays` 配置，征召时写入批次，不受之后文化或配置变化影响。
- 工资减免按 `CharacterObject -> 数量` 精确计算，不再使用只记录总人数的 `FiefWageExemptionManager`。
- 未继续使用针对 `DefaultClanFinanceModel` 的 Harmony 补丁；该补丁会在战役初始化期间过早触发本体财务模型静态初始化。工资模型只读取已经完成对账的服役记录。

## 5. 每日对账

`FiefPartyManager` 每日以 Party 为单位核对所有来源封邑的在役批次：

1. 优先匹配 Party 名册中的完全相同兵种。
2. 剩余人数只允许在真实升级链上双向匹配。
3. 使用容量图和最大流求最大合法匹配人数，避免遍历顺序导致错误战损。
4. 多个批次竞争同一实际兵员时，按登记人数比例分配，余数按稳定批次 ID 处理。
5. 对账结果写回实际兵种；无法匹配的登记人数视为战损。
6. 空批次从来源封邑和运行期索引中移除。

粗略的步兵、骑兵分类不能代替升级链判定；只有直接或间接升级关系成立的兵种才能互相代表。

## 6. 转移、解散与驻军捐赠

- Mod 的部队解散并入驻军流程会在源 Party 名册清空前转移对应服役批次。
- 驻军捐兵流程通过转移前后名册差额识别实际移动的兵员，并把相应服役身份转给接收 Party。
- Party 被移除后，仍绑定该 Party 的批次按损失处理：释放封邑兵额，但不恢复 Hearth。
- 来源封邑易主不会自动证明在外士兵已经死亡，因此新结构的有效在役批次不会仅因所有权变化而被静默删除。

## 7. 主动返乡

- 返乡前先推进服役时间并对目标 Party 做一次对账。
- 只处理“指定来源封邑 + 指定 Party”的有效批次。
- 只移除 Party 名册中真实存在、可与登记记录匹配的士兵。
- 实际返乡人数恢复对应 Hearth，并进入 `FiefReturnBatch` 冷却。
- 冷却结束后兵员重新进入封邑就绪名册。

## 9. 当前兼容性结论

- 新档：从第一次征召开始建立完整的新服役记录。
- 旧档：可以继续加载，但旧分遣队跟踪直接作废；旧 Party 中已经存在的士兵保留为普通士兵，不享受旧记录对应的免薪，也不能通过旧记录返乡。
- 保存新记录后再次读取：按 Party ID 重建运行期索引，继续服役计时、对账和免薪。
